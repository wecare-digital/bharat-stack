.home-flow — the home page section below the hero

Measured on the built export at eleven viewport widths. The hero above it was corrected in #55; this is the next section down. Four findings, three of them confined to one band of widths that no breakpoint currently owns. Nothing here changes the layout's design — two columns on desktop, copy above panel on narrow — only the numbers that got left behind.

Flaw 1 · worst offender

Between 768px and 1024px the line length more than doubles

The copy column sits in a fixed 380px track on desktop, which is a proper typographic measure — 47 characters per line. At 1024px and below the grid collapses to one column and the column inherits the full page width with no max-width at all, so the same paragraph runs 120 characters. The convention is 45–75; 120 is 1.6× the upper bound. Both neighbours on this very page already cap themselves — .home-sub at 560px and .home-close-lead at 782px — so this column is the outlier on its own page.

Flaw 2 · nobody owns this band

The layout collapses at 1024px; the terminal only shrinks at 767px

Two breakpoints were set independently and they do not meet. .home-flow drops to one column at max-width:1024px. .wt-window steps its height from 650px down to 560px at max-width:767px. Everything between 768px and 1024px therefore gets the narrow layout and the desktop panel height: a 650px black panel at 100% of the measure with nothing beside it. That is verbatim the condition the code comment says the two-column band was introduced to remove — it was removed from desktop and left in the tablet band. Flaw 3 · site-wide, needs your call

The h2 tracking is a fixed pixel against a fluid font size

letter-spacing:-1.2px on font-size:clamp(28px,3.2vw,40px) is not one setting, it is a different setting at every width: −3.00% at 40px, −3.66% at 32.8px, −4.29% at 28px — a 1.43× swing. This is the same defect corrected on the hero h1 in #55, where -2.2px became -0.04em. The consequence of that fix is that the h1 is now a flat −4.00% at every width while this h2 drifts, so on a desktop screen the page's two biggest headings are tracked differently (−4.00% vs −3.00%) for no reason a reader could name.

-0.03em is chosen so the desktop rendering does not move at all — −0.03 × 40px is exactly −1.2px. Only the narrow end changes, and it changes toward the value desktop already has.

This one is not a local edit, and I have not applied it. The comment above the rule records that .home-flow-title is byte-for-byte identical to .home-close-title, .cl-h2, .mo-h2, .brx-h2 and .pdp-h2 — 12 headings across 10 public pages — and instructs that node tools/browser/typecheck.js be run before it is changed. Changing it here alone would split a rung that is currently consistent; changing it everywhere is a site-wide typography decision. It also does not match .kiro/steering/grahak-os-design.md, which specifies clamp(32px,4.2vw,54px) — a gap that already exists and is already reported by typecheck.js. Tell me which: this section only, all 12 headings, or leave it and log it.
Flaw 4 · minor, probably leave

The two columns end 136px apart on desktop

The panel is a hard height:650px; the copy column measures 514px. So the band has a ragged bottom edge of 136px at 1280, 1440 and 1920 — the copy stops, and the black panel continues past it. align-items:start is deliberate and correct (centring the copy against a 650px panel would leave a gap above and below), so this is the cost of a fixed-height panel beside fluid prose, not a bug. Worth stating rather than fixing: closing 136px would mean either padding the copy with something it does not need, or shortening the transcript.
