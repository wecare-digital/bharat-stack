# WhatsApp payments, India — the contract this repo actually implements

This file was **0 bytes** until 2026-09-28 while being an always-on steering file, which
is worse than not existing: it occupied a slot that reads as "the payments rules are
written down". Task 1.5 of `.kiro/specs/whatsapp-wix-commerce/tasks.md` asks for it.

Everything below is drawn from committed source and from the requirement registry. Where
a value could not be confirmed from source it says so rather than guessing. **No
credential, key id or secret value appears here** — only names and paths.

## One gateway, and it is Razorpay

Razorpay is the only payment gateway. PayU is retired and its secret is permanently
gone (`DeleteSecret` 2026-08-26, 30-day window elapsed, now
`ResourceNotFoundException`). Re-introducing PayU is a standing refusal, not a decision.

| Concern | Where |
|---|---|
| Webhook handler | `amplify/functions/payments/razorpay-webhook/handler.py` |
| Credential | Secrets Manager `wecare/razorpay/api` — **both** `key_id` and `key_secret` |
| Legacy path | `wecare/razorpay-webhook` holds only `webhook_secret`; reading `key_id` from it returns 501 |
| Status vocabulary | `lambda_utils/payment_status.py` |
| Records | `stack-wecare-digital-PaymentsTable` |

The secret path matters and has already caused one outage class: the handler must read
`wecare/razorpay/api`, lazily, at request time. A module-scope read caches the value for
the life of the execution environment, so a rotation does not take effect until every
warm sandbox recycles — fixed in this function on 2026-09-19 and re-confirmed by
`scripts/verify_razorpay_secret_path.py`.

## Two payment configuration names, and they are not interchangeable

Meta's payment configuration is per WABA, and this account has two. The configuration
name travels in the `order_details` interactive message, so sending a WABA1 message
that names WABA2's configuration fails at Meta rather than at our own validation.
`_build_payment_settings` in `messaging/outbound-whatsapp` is the single place that
resolves it — spec task 9.4 says reuse it rather than reimplementing, and that is the
reason.

**Unverified here:** the two configuration *names* are not reproduced in this file. Read
them from the live Graph API or from `config/lambda-env-manifest.json` at the time of
use; a name copied into a steering file is exactly the kind of dated constant
`00-current-owner-overrides.md` forbids quoting.

## India-specific rules

| Item | Value | Why it matters |
|---|---|---|
| MCC | **7392** | Travel/business services. Set on the Razorpay account, not per request |
| Purpose code | **03** | Required on India cross-border/marketplace settlement reporting |
| Currency | `INR` only | Compare currency **explicitly**; never infer it from the amount |
| Minor unit | paise, integer | 1 INR = 100 paise |
| DLT | SMS via AWS End User Messaging `ap-south-1`, sender `WDBEEP`, template key `ivr-default` | An India SMS without a registered DLT template is rejected by the carrier, not by AWS |

### Money is integer paise, everywhere

R6.1 requires no float arithmetic anywhere in the payment path, and the reason is
specific rather than stylistic: `0.1 + 0.2` is not `0.3` in binary floating point, and a
one-paise mismatch against the checkout total must **fail closed** (R6.2), so a rounding
artefact becomes a refused order. `Decimal(str(value))` is the pattern already used
throughout the handlers for DynamoDB numbers; apply the same discipline before the
comparison, not after.

A known latent defect sits here: `_money_amount` passes a non-numeric price through as
`str(value)`, so a junk price would travel into a Wix payload. Latent only because Wix
writes are switched off.

## `reference_id` rules

`reference_id` is the identifier that ties a WhatsApp payment back to an order, and it
is the join key three separate subsystems agree on.

1. **It is generated by us, not by Meta.** `REFERENCE#<metaReferenceId>` is the
   resolve-before-generate index (spec task 2.3), so a replayed Meta event resolves to
   the order that already exists instead of minting a second one.
2. **It must be stable across retries.** The whole reconciliation pipeline is keyed on
   it; a fresh id on retry produces a duplicate paid order, which is the one failure
   this domain must never have.
3. **It is not a secret and it is not a phone number**, so it may be logged in full.
   That is deliberate: it is the correlation id that lets a log line be traced without
   any masked field, which is why `contactId` and `referenceId` appear together in
   almost every payment log.
4. Order numbers are separate and reserved conditionally under `ORDERNO#<number>`
   (task 2.1). `_get_or_create_wd_order_number`'s exception path currently returns an
   **unstored** number — task 2.2 removes it, because a number that exists only in a
   response is a duplicate waiting to be issued.

## Payment status has three vocabularies and one of them must win

`lambda_utils/payment_status.py` documents a `paid` versus `captured` disagreement
across three tables and maps every measured spelling onto one ladder. **Do not infer a
state from a string comparison** — go through `payment_status`, which also owns monotonic
ordering so a late webhook cannot move an order backwards.

**Landed 2026-09-30, and the distinction matters.** The module always did the mapping; what
it lacked was callers. Four handlers compared raw strings and imported nothing, so the
vocabulary was correct and unconsulted. Every *decision* now routes through it —
`invoice-engine`, `inbound-whatsapp-handler`, `outbound-whatsapp`,
`whatsapp-business-api` (+ `flows/track_request`) and `secure-files/razorpay_orders` — and
three of those comparisons were failing in the dangerous direction:

| Site | Raw comparison | Consequence of `paid` |
|---|---|---|
| `invoice-engine.cancel_invoice` | `== 'captured'` | a **paid invoice was cancellable** |
| `invoice-engine` dedup update | required `'paid'` **and** `'captured'` | invoice stayed unpaid, permanently, silently |
| `inbound-whatsapp-handler` Meta lookup | `!= 'captured'` | a confirmed capture recorded `REJECTED_MISMATCH` |
| `outbound-whatsapp` order status | `== 'completed' or == 'captured'` | a paying customer told "Payment failed" |

Two boundaries, both deliberate and both pinned by tests:

- **`InvoicesTable.status` is NOT this vocabulary.** It is a document lifecycle
  (`created` → `sent` → `paid` → `cancelled`), so `inv.get('status') != 'paid'` is
  *correct* and was left alone. `for_storage`'s docstring says the module does not own
  that field. "Finishing the job" by canonicalising it would collapse two different facts
  about one row.
- **Only `captured` is banned as a raw literal**, by
  `tests/test_payment_vocabulary_at_decision_points.py`. `captured` belongs exclusively to
  the payment vocabulary, and banning it catches the dangerous direction — `== 'captured'`
  is the comparison that misses `paid`. Banning `paid` too would fail on the correct
  lifecycle code above. The gate walks the **AST**, not the text, because the comments
  explaining the rule necessarily contain the forbidden literal.

## What is prohibited, and generates no prompt

- Payment capture, refund, or any payment-configuration mutation.
- Creating a standalone Wix invoice. A billing document must be order-linked (R9.2), and
  `wixInvoices` reports NOT AVAILABLE on this site anyway.
- Any second charge. R7.4 wants an explicit test enumerating the Wix calls the
  reconciliation path can make, precisely so "it cannot charge again" is demonstrated
  rather than asserted.
- Enabling a live-send flag to test a payment flow.
