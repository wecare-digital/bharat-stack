# Wix coupons and gift cards: issuance store, bearer-value ledger, Wix SPI plugin

Five new shared modules, three new Lambdas with their own roles, six provisioner scripts and
eleven test files land the coupon and gift-card features from the completed design. The coupon
side keeps its code as the partition key and lets Wix own every discount arithmetic; the gift-card
side makes the code bearer value behind an HMAC-with-pepper and settles its leg on a second,
forward-only stage ladder that never touches the Razorpay verification machinery. All 20
design-review findings are resolved in code, each with a test, and the four shared gates
(deploy registry, drift allowance, payment-vocabulary raw scan, `provision_checkout.py --verify`)
were opened in one visit rather than four.

Watch for: the push that landed this work triggered `seo-tools-deploy.yml` and replaced a live
Lambda's `$LATEST`, which the execution record discloses in its Rollback column while its
Authority column says "no production mutation" (confirmed against the live account); and
`gift_card_store.void()` latches `voidedBy` before crediting with no recovery marker, so a
transient failure between the two strands the credit permanently (confirmed by reading the code,
and by the absence of the `settled`-style flag the redeem path has).

**Verdict**: NEEDS_CHANGES

## High-level view

Money is integer paise end to end and the discipline is structural rather than promised.
`money.positive_paise` refuses a float, a bool and a fractional `Decimal` by type; the SPI's JSON
numbers are parsed `parse_float=Decimal` before any of our own logic runs; and the SPI response
renders `50.00` by integer division and `%02d` into a substituted marker so no float is
constructed even on the way out. Two tests patch `float` to raise and run the whole money path
under it.

The two codes are treated as opposites and both halves are pinned. A coupon code is the partition
key and may be logged in full because it is broadcast marketing material; a gift-card code is
`HMAC-SHA256(pepper, NFKC(code).upper())`, never stored in clear, never in a path or query, with
`masked()` refusing anything longer than four characters so a full code cannot be truncated inside
a logging expression by mistake. PIN comparison is `hmac.compare_digest`, asserted over the AST.
A malformed code, an unknown code and a wrong PIN all answer `GiftCardNotFound`, so the endpoint
is not a validity oracle.

Every balance move is a `ConditionExpression`, never a read-modify-write. The `GCORDER#` claim is
a conditional put written before the decrement and carries `settled: False`, which is what makes
an insufficient-balance failure replayable rather than a redemption that never moved money.
Redemption is idempotent per `(codeHash, paymentAttemptId)` and per `(code, orderId)` on the
coupon side, and a same-key-different-amount replay is surfaced as `REDEEM_AMOUNT_CONFLICT`
instead of being reconciled. DECISION 5 moves the hold existence fact onto the row whose key is
already known, so `hold()` is one conditional `UpdateItem` with no preceding read and there is no
`Scan`, no prefix query and no second index anywhere in either store.

The settlement ladder is built like `payment_status`: string stage values, a separate rank map
read through a `.get` default of 0, and the rank persisted so the forward-only guard is one
numeric comparison inside DynamoDB. `GC_VOIDED` outranks `GC_REDEEMED` so a late redeem cannot
un-void a card. `is_fully_settled` never raises on a missing attribute and requires the two legs
to close against the frozen payable using the amount the provider confirmed, not the amount we
asked for.

JWT verification runs before the route lookup and before any table access, fails closed at every
step, and refuses a multi-valued `aud` rather than searching it. The algorithm allowlist is the
decision, not the token's `alg`. The `cryptography` import is guarded for a packaging reason and
the guard's failure mode is a 401, never a skipped signature check.

Each new Lambda has its own role scoped to its own table, no statement was added to the shared
`wecare-digital-lambda-role`, and no role carries `dynamodb:Scan` or a wildcard. The gift-card
table is CMK-encrypted under an alias with `kms:ViaService` bounding both grants, PITR on and TTL
off, both asserted in `--verify`. The one shared-role edit, `wecare-checkout-role` gaining
`DeleteItem`, is scoped to the two new tables and the contract test that used to ban `DeleteItem`
outright was strengthened into "no statement granting `DeleteItem` names either evidence table"
rather than deleted.

No do-not-touch file was modified by any of the six commits. Nothing in the diff publishes,
moves an alias, or enables a flag; every provisioner defaults to a dry run. The one production
mutation is the incidental one in the first issue below.

### The void path is not recoverable, and the redeem path next to it is

`redeem()` is careful about exactly this hazard. The claim row goes in first with `settled: False`,
the decrement flips it, and the docstring explains that the flag is what makes an
insufficient-balance failure replayable "rather than reporting a redemption that never moved
money". `tests/test_gift_card_store.py::test_the_claim_row_is_settled_by_the_decrement_so_a_short_balance_is_recoverable`
pins it.

`void()` does not have that device:

```python
table.update_item(... UpdateExpression="SET voidedBy = :void, voidedAt = :at",
                  ConditionExpression="attribute_not_exists(voidedBy)", ...)
# ... then:
balance_after = credit(table, code_hash=digest, amount_paise=amount, clock=clock)
```

Guard first, credit second. The ordering itself is right and the docstring gives the reason — the
reverse order could credit twice if the guard lost its race. The gap is that the guard latches
unconditionally, so if `credit()` raises (a throttle surfaces as `GiftCardStoreUnavailable`, or the
balance ceiling surfaces as `BALANCE_CEILING_EXCEEDED`), the transaction is marked voided forever
and the money was never returned. Every retry re-reads `original.get("voidedBy")` and raises
`AlreadyVoided`. Unlike the redeem path there is no marker a retry can distinguish, and the only
`arm_failure` in the gift-card store suite is on `get_item`, so no test exercises it.

This is a NIT rather than a MEDIUM because of reachability, not because the hole is not real.
`void()` is only called from the SPI's `/v1/void`, which needs a `transactionId` Wix can only have
learned from a `/v1/redeem` response; section 1.3 predicts Wix never calls `/v1/redeem` at all, that
prediction is alarmed at a threshold of one occurrence, and the SPI routes are not provisioned yet.
The fix is small and matches a device already in the file.

### One narrow PIN-path disclosure, reported rather than raised

`_pin()` coerces to `str`, so a non-string PIN cannot reach `pin_hash` and the type-confusion
oracle that would otherwise open is closed. A PIN longer than `MAX_PIN_LENGTH` does still answer
`400 INVALID_PIN` where a wrong PIN answers `404 GiftCardNotFound`, which distinguishes a
PIN-protected card from an unprotected one. Not raised as a finding: `assert_spendable` refuses an
unknown code first, so the distinction is only visible to a caller who already holds a valid code,
and what it reveals is whether a card they can already query has a PIN.

### The shared `--verify` gate had a trap in it

`simulate_principal_policy`'s results were aggregated per action across every resource, so once
`DeleteItem` is legitimately allowed on two tables and legitimately denied on two others, the
aggregate becomes `{"allowed", "implicitDeny"}` and a correctly provisioned role fails its own
gate. The only way to quiet that without re-keying is to widen the role, which is the wrong
direction.

The verdict loop now keys on `(EvalActionName, EvalResourceName)` against an explicit
`_EXPECTED_DENY`, which turns the withholding into something measured: a `DeleteItem` that becomes
ALLOWED on `PaymentAttemptsTable` or `WixOrderIds` is now reported, where a per-action aggregate
could not tell that apart from the coupon grant it was supposed to see. The contract test's fake
IAM had to change with it, to one result per `(action, resource)` pair carrying
`EvalResourceName` — the old per-action shape matched the real API only while every action had the
same answer on every table.

the principle. The reasoning is written into both module docstrings rather than left to be
re-derived, and the same judgement is applied consistently to 52a, 107a and 113b. The resulting
state is strictly stronger than the plan asked for: an unconditional assertion instead of a
deferred one.

removing them safe by deletion: had the grant not actually landed, each would have failed rather
than passed quietly.
