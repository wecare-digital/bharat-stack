# Wix coupons and gift cards, pass 3: the marker fix is right, and then it deletes the marker

REV-3, REV-4 and REV-5 are all addressed. Each money move now writes its own idempotency marker on
the card row inside the same conditional `UpdateItem` that moves the balance —
`appliedClaim#<paymentAttemptId>` on the decrement, `appliedVoid#<voidTransactionId>` on the credit
— so the window the previous pass reproduced is closed: failing only `SET settled = :true` or
`SET credited = :true` now costs a lost condition on retry instead of a second balance move. I
re-ran the full tree at HEAD `180e180e` myself: `6793 passed, 1 skipped, 7 xfailed in 58.52s`,
zero failed, zero xpassed. I also mutation-tested the fix by deleting both
`attribute_not_exists(#applied)` clauses, which kills four of the five new tests — they are gates,
not decoration.

The problem is the last line of each path. `_drop_applied_marker` removes the marker once the flag
has landed, on the stated ground that "nothing consults the marker again". That holds for a replay
that *starts* after the flag is written. It does not hold for a request already past the flag read
and not yet at the money move, and in that interleaving the drop hands back the exact double-move
the marker was added to prevent.

Watch for: `redeem()` debits twice for one `paymentAttemptId` when a stalled request resumes after
a concurrent retry completed and dropped the marker (confirmed, reproduced, final balance 10000
where 30000 is correct, one `GCTXN#` row); `void()` credits twice in the same shape (confirmed,
reproduced, 90000 where 50000 is correct).

**Verdict**: NEEDS_CHANGES

## High-level view

`credit()` takes `once_key` as an option rather than becoming unconditionally idempotent, which is
the distinction that matters: two top-ups of the same size are two events, two retries of one void
are not.

The marker is then deleted at the end of the happy path, which makes the money move's only
idempotency record a transient lock whose lifetime is "until someone else finishes". A process that
read `settled: False` (or `credited: False`) before the drop finds no marker when it finally reaches
its `UpdateItem`, and `balancePaise >= :amount` stops an overdraw, not a second deduction while
funds remain, so the move lands. One `GCTXN#` row, two debits, no error. The previous pass's window
needed a failed marker write; this one needs only a slow process and a client retry, which is the
ordinary shape of a Lambda invoked twice for one logical request.

The growth argument behind the drop is real but it is not an argument for deleting the lock. A
marker name is at most 141 bytes and in practice a ULID attempt id makes it about 40, so a card
accumulates roughly that per redemption against DynamoDB's 400 KB item cap. Nothing bounds the
redemption count from below — a gift-card leg has no minimum — so "keep every marker forever" is
genuinely unsatisfactory. The resolution is to make the drop safe rather than to drop early: bind
the money move to the flag row so that a late arrival whose flag has already flipped cannot move
money at all.

Separately, the recovery replay reports the balance as at the replay rather than as at the move it
is recovering, and `_decrement` writes that figure into the `GCTXN#` row's `balanceAfterPaise`.
With a second purchase interleaved, two transaction rows record the same `balanceAfterPaise` and
one of them was never true. `credit()` documents this trade-off in its own docstring; the
redemption path does not, and the redemption path is the one whose figure lands in the ledger.

The §12.1 round-up added to `coupons-giftcards-build-20261001.md` overstates two measurements. It
says the xfail inventory "still equals DECISION 8's list exactly" when DECISION 8 enumerates nine
tests and seven are marked, and it says all five new tests fail under the mutation when four do.
The seven-against-nine deviation itself is not a finding and I reach that conclusion independently
for the third time — tests 100 and 113 assert properties that hold today, so a strict mark would
XPASS, which `context.json` counts as a failure — but a document asserting there is no deviation
removes the reader's chance to re-derive that.

### The marker is a lock whose lifetime is shorter than the thing it locks

```python
balance_after = _decrement(table, digest=digest, amount=amount, attempt=attempt, now=now)
_mark_settled(table, claim_row_key, balance_after=balance_after, now=now)
_drop_applied_marker(table, digest, APPLIED_CLAIM_PREFIX + attempt)
```

`_drop_applied_marker`'s docstring states the safety argument explicitly: "Once the claim reads
`settled` … the replay short-circuits before it reaches the money move, so nothing consults the
marker again." The quantifier is the problem. A replay that *begins* after `settled` is written
does short-circuit, at the `existing.get("settled")` branch in `redeem`. A request that passed that
branch while the claim still read `False` has already made its decision and will reach
`_decrement` regardless of what happens to the flag afterwards.

That is the ordinary double-invoke shape, not an exotic one: request 1 wins the claim put and
stalls, the client retries, request 2 finds the unsettled claim, completes the whole redemption and
drops the marker, request 1 then resumes into `_decrement` and finds nothing stopping it.

```
issued             50000
   [R1 stalled at its decrement; R2 runs the whole redemption]
   R2 committed    True balance 30000
   markers after R2 []
R1 returned         True balance 10000
FINAL balancePaise  10000  (correct value is 30000)
GCTXN rows          1
```

20000 paise taken twice under one `paymentAttemptId`, one transaction row, both calls reporting
`committed: True`. The void path is identical, because `void` re-drives under the void id read back
off the latch and so arrives with the same `once_key` after the marker is gone:

```
after redeem       10000
   [R1 stalled at its credit; R2 completes the void]
   R2 void balance 50000 markers []
R1 void balance    90000
FINAL balancePaise 90000  (correct value is 50000)
```

`test_an_applied_move_marker_does_not_outlive_the_move_it_guards` encodes the unsound half of the
argument in a comment — "A dropped marker is safe because the flag it hands over to is already
written: the replay never reaches the money move again" — and then demonstrates it only with
replays that start after the flag is written, which is the case where it is true.

This is not a regression against the pre-fix code; the same interleaving double-moved before the
marker existed. It is a gap against the criterion the fix sets for itself, in `_decrement`'s own
words: "exactly once per attempt rather than merely once per request that gets this far".

### Why the growth argument does not settle it

The reason given for dropping is the 400 KB item cap, and that reason is sound as far as it goes.
`_identifier` caps an attempt id at 128 characters, so `appliedClaim#` plus an id is at most 141
bytes; a ULID attempt id makes it about 40 including the timestamp value. Nothing bounds a card's
redemption count from below, because the gift-card leg has no minimum amount —
`RAZORPAY_MIN_LEG_PAISE` constrains the Razorpay leg, not this one — so a card really could
accumulate markers without a natural ceiling, and "never drop" is not the answer either.

What closes the window without unbounded growth is making the flag row part of the money move's
condition, so that the flag — which is permanent — carries the exclusion once the marker is gone:

```
TransactWriteItems:
  Update       GCCARD#<digest>    ADD balancePaise :neg  SET #applied = :at
                                  under attribute_not_exists(#applied) AND balancePaise >= :amount
  ConditionCheck GCORDER#<digest>#<attempt>   settled = :false
```

A stalled request whose claim has since settled loses the `ConditionCheck` and moves nothing, which
is exactly the state the drop currently leaves undefended. Both items are in `GiftCardsTable`, so
no role crosses a resource boundary, but a transaction does need `dynamodb:ConditionCheckItem` on
the table and on the index — check whether
`provision_checkout.py::_package_needs_transactions` starts reporting that grant once
`gift_card_store` is inside the checkout import closure, since `finalization.py` owns SEAM-G5.

Whichever shape is chosen, the test that pins it has to drive the interleaving rather than the
write failure: a fake that lets a second, complete redemption run from inside the first one's
decrement call, asserting the balance moved once. The five committed tests all aim their fault at a
write, so none of them can see this.

### A recovered redemption records a balance that was never true

`_decrement`'s marker-present branch answers with the card's current balance, and `redeem` writes
that straight into the `GCTXN#` row:

```
attempt-1 settle write failed; balance now 30000
GCTXN attempt-1 amount 20000 balanceAfterPaise 25000
GCTXN attempt-2 amount 5000  balanceAfterPaise 25000
card balance 25000
```

`attempt-1` debited 20000 from 50000 and left 30000. Its ledger row says 25000, which is what the
card held after `attempt-2` also debited. Two rows now claim the same `balanceAfterPaise` and one of
them is not a balance this card ever had after that move. §6.3 enumerates `balanceAfterPaise` as a
transaction attribute, and reconciliation reads these rows.

`credit()` names this trade-off in its own docstring — "the returned balance is the card's balance
AS AT THE REPLAY … used for a record rather than for a decision" — and accepts it. The redemption
path makes the same trade silently, and it is the path whose figure a reconciliation run reads. The
interleaving is not hypothetical: `test_a_stalled_redemption_still_debits_once_when_another_purchase_lands_between`
already constructs it and asserts only the balance, not the row.
