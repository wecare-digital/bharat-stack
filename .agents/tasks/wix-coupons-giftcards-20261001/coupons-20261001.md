# Coupons — design, 2026-10-01 (revision 3)

Owner intent, verbatim: *"A CUPPON CREATE CAN MENAIN IN TABLE AND LAMBE ... ALL CREATE CAN BE
USED USED IN CHECOUT"* — coupons are created and held in our own DynamoDB table by our own
Lambda, and are usable at checkout.

This is **additive new capability**, not a migration. Nothing here changes the active
architecture: WECARE remains a self-managed Next.js/AWS application using Wix headlessly, AWS
owns authentication and payment orchestration, payment is Razorpay Standard Checkout on our own
site, and the Wix order is created only after authoritative payment verification. No customer is
ever routed to a Wix-hosted checkout page and `Get Checkout URL` is not called.

Every API-shape claim below carries a `dev.wix.com` URL. Each page was fetched live on 2026-10-01
and every schema, every quoted sentence and every example body was read out of the OpenAPI
document and the article markdown the docs pages embed — not from a rendered table, not from a
summary, not from training data. Where the live contract contradicts what this repo currently
sends, that is recorded as a finding rather than smoothed over.

**Revision 3** resolves the second-pass findings in `design-review.json` (6 HIGH, 12 MEDIUM,
4 NIT; the HIGH findings are all against the gift-card document). The responses are itemised
in §12. Two changes alter the design rather than correcting a detail: `WIX_CODE_CONFLICT` is
**withdrawn as an automatic outcome**, because `Create Coupon` documents no errors at all
(MEDIUM-9, re-fetched and measured below), and this document now owns **three** shared-gate edits
rather than two, the third being the `deploy_all_lambdas.py` registry (MEDIUM-13).

Revision 2's two shape changes stand: coupon money leaves as a **whole-rupee JSON integer**, and
the real `compute_quote` insertion point is `amplify/functions/ecommerce/checkout/handler.py`,
already wired.

#### 1.1.2 Update A Coupon — transcribed, and it is a PATCH (closes HIGH-6)

    PATCH https://www.wixapis.com/stores/v2/coupons/{id}

https://dev.wix.com/docs/api-reference/business-solutions/coupons/coupons/update-a-coupon

`operationId: wix.coupons.api.v2.CouponsV2.Update`, maturity `GA`, permission `COUPONS.MANAGE`
(**Manage Coupons**), `isAdminMethod: true`. Path parameter `id` (string, required).

**The semantics are documented explicitly, and they are patch, not replace.** Quoted from the
method description:

> Updates a coupon. Only the properties passed in the `specification` object will be updated. All
> other properties will remain the same. To remove a value from the coupon, pass its corresponding
> property with a value of `null`. When updating a coupon, you cannot change the coupon's `type`.
> For example, if the coupon's `type` is `moneyOffAmount`, you cannot change it to
> `fixedPriceAmount`. You can update the coupon type's value. For example, you can change the value
> of `moneyOffAmount` from `5` to `10`.

`UpdateCouponRequest` body:

```
fieldMask      { paths: [string] }        optional
specification  Specification              the §1.1 shape, all fields optional
```

Response is `UpdateCouponResponse`, and the documented example response body is `{}` — empty.

Documented example request, verbatim:

```
curl -X PATCH 'https://www.wixapis.com/stores/v2/coupons/6df8d9ea-9e31-49af-b272-5e22861cce92' \
  -H 'Content-Type: application/json' -H 'Authorization: <AUTH>' \
  --data-binary '{ "specification": { "active": false } }'
```

**This settles the deactivate route's shape.** `aws-agent-rules.md` says to treat "update" in an
API as "replace" until proven otherwise; here it *is* proven otherwise, by the method's own prose
and by an official example that sends `active: false` and nothing else. So
`POST /coupons/{code}/deactivate` sends exactly `{"specification": {"active": false}}` and cannot
wipe the discount, scope, limits or expiry. A test asserts the outgoing body carries *only*
`specification.active` — the narrow body is the safe one here, and a full re-send would be the
risky choice because it would re-assert fields whose Wix-side values we may not be the last writer
of.

`fieldMask` is **not** sent. It is optional, the documented example omits it, and sending a mask
we have not measured the behaviour of would reintroduce exactly the replace-semantics risk this
section removes.

Two things follow. First, **Remove Coupon requires `couponId`**, which V1 did not — so the
`coupons[0].id` returned on the cart must be retained, not just the code. Second:

> **FINDING — `cart_v2.add_coupon` sends the V1 field name.** `cart_v2.py` currently posts
> `body={"couponCode": code.strip()}`. The live V2 request body is `{"coupon": {"code": code}}`,
> and `coupon` *and* `coupon.code` are both in the schema's `required` array, so the current call
> cannot succeed. This is not an ambiguity in the docs — the Cart V2 migration mapping states the
> rename explicitly (*`couponCode` → `coupons[0].code`*,
> https://dev.wix.com/docs/api-reference/business-solutions/e-commerce/purchase-flow/cart-v2/migration-mapping)
> and every occurrence of `couponCode` on the Add Coupon page is error data or a discount-source
> annotation (`InvalidCouponCodeErrorData.couponCode`, `Discount.couponCode`), never the request
> body. `cart_v2.py` is owned by another session, so this is **SEAM-C1** (§8) and is not edited
> here. It is listed first because until it is fixed, no coupon can be applied at all.

> **FINDING — the live adapter's length bound is wider than the V2 schema's (closes NIT-20).**
> `CouponInput.code` is `maxLength 50`. `cart_v2.py` refuses a code only above **100**
> characters (`len(code.strip()) > 100`), which `tests/test_wix_cart_v2_coupons_and_stock.py:184`
> pins by parametrising `"x" * 101` among its rejected inputs. So a 51-to-100 character code
> passes our validation and is refused by Wix. Our own `wecare-coupons` validation is tighter
> still — 20 characters, Wix's documented `Specification.code` maximum (§1.1) — so a coupon
> *we* issued can never hit either bound. The gap only matters for a code typed straight into
> the cart adapter, which is why the correction is folded into **SEAM-C1** (§8) rather than
> raised separately: the same edit that fixes the field name should fix the bound, and two trips
> to another session's file for one function is one trip too many.

**One coupon per cart**, quoted from the Cart V2 introduction
(https://dev.wix.com/docs/api-reference/business-solutions/e-commerce/purchase-flow/cart-v2/introduction):

> Carts currently support a single coupon and a single gift card at a time. Attempting to add a
> second returns an error.

The same page carries a constraint worth recording even though nothing here uses it, because it is
one-shot: *"`CartSettings` can only be set when creating a cart and can't be changed afterward.
These settings control checkout page behavior, such as locking coupons or gift cards from being
modified during checkout."* A later decision to lock coupons at checkout would have to be taken at
cart-creation time, in `customer_cart`, not here.

Documented failure shapes on Add Coupon, from the method's own `errors[]`:

### 1.3 Where the discount lands

    POST https://www.wixapis.com/ecom/v2/carts/{cartId}/calculate
    POST https://www.wixapis.com/ecom/v2/carts/{cartId}/estimate

https://dev.wix.com/docs/api-reference/business-solutions/e-commerce/purchase-flow/cart-v2/calculate-cart
https://dev.wix.com/docs/api-reference/business-solutions/e-commerce/purchase-flow/cart-v2/estimate-cart

Quoted from the Cart V2 introduction:

> **Calculate Cart**: Performs a full calculation of cart totals including all price components
> (subtotal, delivery, taxes, fees, gift cards, and discounts). Use this when you need the complete
> pricing breakdown, such as before checkout. Always runs checkout-level validations.
>
> **Estimate Cart**: Performs a partial, component-based estimation controlled by boolean flags
> (`calculateDelivery`, `calculateTax`, `calculateAdditionalFees`, `calculateGiftCards`). Components
> not explicitly enabled are excluded from the calculation.

Both are already wrapped by `cart_v2.calculate()` / `.estimate()`. `CalculateCartRequest` is
`{cartId, refreshCart}`; the response is `{cart: Cart, summary: CartSummary}`.

A coupon reduces `summary.priceSummary.discount`. The field's own description, verbatim:

> Cart subtotal discount amount, deducted from the subtotal. Item-level discounts are already
> reflected in the subtotal. Returns 0 when no cart subtotal discount is applied. For details of
> all applied discounts (including delivery discounts), see `cartSummary.discounts`. Currently,
> only a single coupon is supported.

So Cart V2 defines `subtotal` as line prices after item-level automatic discounts but **before**
cart-level discounts, and the existing reconciliation in `cart_v2.calculate` —

    subtotal - discount + delivery + additionalFees + tax == total

— already accounts for a coupon and needs no widening.
`tests/test_wix_cart_v2_coupons_and_stock.py` already pins this
(`test_a_coupon_reduces_the_discount_component_not_the_subtotal` at line 107,
`test_a_couponed_quote_still_reconciles_exactly` at line 116,
`test_a_coupon_lowers_the_convenience_fee_basis` at line 134).

Every money field in `wix.ecom.cart.v2.PriceSummary` is a `ConvertedMoney`, whose `amount` is
`string` with `format: DECIMAL_VALUE`. That is why `Money.from_wix` works on the cart path and the
coupon path needs different treatment — the cart sends strings, the coupon service sends numbers.

**`Create Checkout From Cart` has no V2 equivalent.** The V2 flow is Update Cart + Set Delivery
Method then Place Order directly
(https://dev.wix.com/docs/api-reference/business-solutions/e-commerce/purchase-flow/cart-v2/place-order).
We do not call Place Order. Its own description, verbatim: *"Completes checkout and creates an
order. This endpoint may charge the customer."* — and its scope is `Write Carts V2 (PII)`.
`cart_v2.py` structurally omits it. We collect through Razorpay and record the order afterwards
through `wix_writeback`.

## 2. DECISION 1 — coupon reconciliation: option (a), mirror into the Wix cart

**Chosen: (a). The coupon is mirrored into Wix and applied to the Wix cart with `Add Coupon`, so
the Wix-side total is already net of the discount and our charged amount is derived from it.**

Rejected: (b), recording the discount on the Wix order through `appliedDiscounts`. Option (b) is
genuinely available — `Create Order` (`POST https://www.wixapis.com/ecom/v1/orders`) accepts
`appliedDiscounts[]` of `com.wix.ecom.orders.v1.AppliedDiscount`, measured as:

```
AppliedDiscount
  discountType       enum  GLOBAL | SPECIFIC_ITEMS | SHIPPING
  id                 string GUID
  lineItemIds        array  DEPRECATED, "Use lineItemDiscounts instead"
  lineItemDiscounts  array
  oneOf DiscountSource:
    coupon           { id, code, name, amount: Price }
    merchantDiscount { ... }
    discountRule     { ... }
```
https://dev.wix.com/docs/api-reference/business-solutions/e-commerce/orders/orders/create-order

It is rejected for two reasons:

1. **It creates a second discount arithmetic.** Under (b) we compute the discount and assert it
   to Wix; under (a) Wix computes it and we consume the result. Two independent computations of
   one number is precisely the writeback-mismatch class this decision exists to close. Under (a)
   a mismatch is not merely detected, it is unrepresentable: there is one number and both sides
   read it.
2. **(b) requires editing `wix_writeback.py` and the order-payload builder**, which another
   session owns. (a) needs no edit to any owned-elsewhere file for the discount itself.

The cited method that makes it reconcile is
`POST /ecom/v2/carts/{cartId}/add-coupon` followed by
`POST /ecom/v2/carts/{cartId}/calculate` — the coupon is applied server-side and the reduced
total arrives from Calculate Cart. A browser supplies a *code*, never an amount.

### 2.1 Two systems, one authority

The owner wants the coupon in our table. Wix needs the coupon to exist Wix-side for `Add Coupon`
to accept the code. Both are satisfied without ambiguity by splitting the two concerns:

| Concern | Authority |
|---|---|
| Issuance, policy, per-customer limits, audit, campaign metadata | **Our DynamoDB table** |
| Discount arithmetic and the resulting cart total | **Wix `Calculate Cart`** |

Creation is a dual write in a fixed order: **claim locally first, then create in Wix.** Local
claim first because the local conditional put is the cheap, reversible half; if the Wix call then
fails we hold a `PENDING_WIX` row that a retry resolves, which is recoverable. The reverse order
would create a Wix coupon our table has no record of — an issued discount with no owner, which
nothing would ever reconcile.

Wix's `code` uniqueness ("Must be unique for all coupons on your site") is the second line of
defence, not the first: our conditional put on the code is the first.

### 2.2 Why `limitPerCustomer` is enforced locally as well

Wix's `Specification.limitPerCustomer` exists, but on this headless path the cart is created
under an admin API-key identity rather than a site member, so Wix cannot reliably attribute a
use to a customer. **Unverified:** whether Wix attributes `limitPerCustomer` at all for a cart
created with an admin identity and no member binding. Nothing on any fetched page states it, and
`Create Coupon`'s `applicableIdentities` is `{"COUPONS.MANAGE": ["APP"]}` — an app identity, with
no member context. Rather than depend on an unmeasured behaviour for a money rule, per-customer
limits are enforced by our own Lambda against our own counter rows (§4), and `limitPerCustomer` is
*also* sent to Wix as defence in depth. If the local check and Wix disagree, the stricter one wins
because the local check runs first and refuses before `Add Coupon` is called.

### 2.3 The quote identity, and the one invariant both documents share

A coupon is a **discount**: it reduces `collection_before_convenience_paise`, so the 2.5%
convenience fee and its 18% GST are computed on the **reduced** total. `compute_quote` needs no
change — it receives a smaller number. `CheckoutQuote.__post_init__` already enforces
`collection + fee + gst == total` (`checkout_pricing.py`), and
`tests/test_wix_cart_v2_coupons_and_stock.py::test_a_coupon_lowers_the_convenience_fee_basis`
already asserts the basis.

The brief asks for "the test that proves Wix order total == Razorpay-charged total". Stated
plainly: **those two are equal only if the convenience fee travels onto the Wix order as an
additional fee, and today the payload builder is the thing that must make that true.**

The convenience fee is our charge, not a Wix supply line. So absent any further action:

    wixOrder.priceSummary.total  ==  collection_before_convenience_paise
    verifiedCapturedPaise        ==  collection + convenienceFee + convenienceGst

…and the two differ by the fee and its GST. But `finalization.accept_paid` calls
`wix_writeback.record_external_payment(..., amount_paise=int(attempt['amountPaise']))`
(`finalization.py`), and on the Cart V2 branch `attempt['amountPaise']` is
`snapshot.quote.total_payable_paise` — the full payable
(`amplify/functions/ecommerce/checkout/handler.py`, the `amount_paise =
snapshot.quote.total_payable_paise` assignment inside `_create`). **Branch matters and is stated
rather than generalised:** on the V1 branch `amountPaise` is
`wix_ecom.authoritative_total_paise(checkout)`, the raw Wix total with no convenience fee, so the
invariant below is asserted for the **Cart V2 branch only**. V1 is the branch this design does not
serve, and `WIX_CART_V2_ENABLED` is the switch between them.

So a payment of the full amount is already recorded against the Wix order. For Wix's own books to
balance, the order must carry the fee. Wix provides the exact vehicle, measured from the
`Create Order` schema:

**The single invariant, stated identically in this document and in

**Every term is integer paise, with the converter written on every Wix term (closes

### 4.1 Row types

```
COUPON#<codeUpper>                         the definition
COUPONUSE#<codeUpper>#<customerId>         per-customer usage counter
COUPONHOLD#<codeUpper>#<cartId>            a short-lived eligibility reservation
COUPONREDEEM#<codeUpper>#<orderId>         idempotent terminal redemption record
```

`codeUpper` is the code upper-cased and NFKC-normalised. Wix says the code must be unique on the
site but does not say it is case-insensitive, so we normalise for *our* key and store the exact
`code` we sent to Wix separately. Comparing on a normalised form is what stops `SAVE10` and
`save10` becoming two coupons that look like one to a customer.

A coupon code is **not** bearer value — it is broadcast marketing material, printed in campaigns
and shared deliberately. So it may be logged in full and is safe as a partition key. This is the
exact opposite of a gift-card code, and the contrast is deliberate: see the gift-card document,
where the same position is occupied by an HMAC.

**Every money attribute is integer paise. Every rate is integer basis points.** There is no float
and no fractional `Decimal` anywhere in the stored shape. `9007199254740991` (`money.py`'s
ceiling) is the upper bound, reused rather than reinvented.

#### Conversion at the Wix boundary — whole rupees as JSON integers (closes HIGH-5)

The earlier draft emitted `Money.to_wix()` (a **string**) into fields §1.1 documents as JSON
`number`, and a `Decimal` for `percentOffRate` through `wix_ecom._request`, whose
`json.dumps(body or {}).encode("utf-8")` has no custom encoder and raises `TypeError` on a
`Decimal`. Neither could run. `wix_ecom.py` is read-only, so the fix cannot be a new encoder there.

**Resolution: restrict the Wix-facing amounts to whole rupees and whole percents, and emit `int`.**

```
moneyOffAmount    <- moneyOffPaise        // 100      # int, e.g. 1234 for ₹1234.00
minimumSubtotal   <- minimumSubtotalPaise // 100      # int
fixedPriceAmount  <- fixedPricePaise      // 100      # int
percentOffRate    <- percentOffBps        // 100      # int, e.g. 5 for 5%
```

A value that is not a whole multiple of 100 is **refused at creation**, with
`400 SUB_RUPEE_DISCOUNT_NOT_SUPPORTED`, rather than rounded. Rounding a discount silently changes
what a customer is promised, and `2500` bps rounded to `25` is a different coupon from `2.5%`.

Why this is the right trade rather than a capitulation:

1. **`int` is unambiguously a JSON `number`.** Every documented example sends integers (`5`,
   `123`, `10`, `30`), so this is the shape Wix demonstrably accepts, with no inference about
   string coercion and no `Decimal` to serialise.
2. **It passes through `wix_ecom._request` unchanged.** `json.dumps` handles `int` natively. The
   adapter needs no encoder, no byte-level request callable and no edit to a read-only module.
3. **No float is ever constructed.** `//` on two ints is an int. A test patches `float` to raise
   and the whole conversion path still runs.
4. **The restriction is honest about scope rather than hiding it.** Sub-rupee coupon discounts are
   out of scope for this release and are named as such in §11, not silently unrepresentable.

The cost is real and is stated: a ₹99.50-off coupon cannot be created until either Wix is measured
accepting a non-integer `number` for these fields, or a `Decimal`-aware serialiser is added
somewhere we own. Both are §11 owner items.

#### Nothing numeric is ever read back from Wix (closes MEDIUM-15)

`wix_ecom._request` returns `json.loads(payload)` with no `parse_float`, so a Wix coupon `number`
would arrive as a **float** before any of our logic ran — `"moneyOffAmount": 10` in §1.1.1's
example response becomes `10.0`. The gift-card document mandates `parse_float=Decimal` at its own
entry point; this path cannot, because `wix_ecom.py` is read-only.

So the rule is stated positively and enforced by test rather than mitigated:

> `wix_coupons` reads exactly three keys from any Wix coupon response: `coupon.id`,
> `coupon.specification.active` and `coupon.specification.type`. It reads **no numeric field,
> ever**. The authority for every money value is our own row, which is also why §2.1 makes our
> table the issuance authority. A Wix response containing `moneyOffAmount` is ignored, not stored.

Test 24a asserts the adapter touches no numeric key, and test 24b feeds it a response carrying
`"moneyOffAmount": 12.34` and asserts nothing numeric is persisted and no float reaches the store.

### 4.3 Counters and holds

`COUPONUSE#<codeUpper>#<customerId>` carries `uses` (N) and is incremented with an atomic `ADD`
under `ConditionExpression: attribute_not_exists(uses) OR uses < :limitPerCustomer`. That is the
per-customer rule; a read-then-write would let two concurrent checkouts both pass.

`COUPONHOLD#<codeUpper>#<cartId>` is the one row type that is permitted to vanish, and it does so
by **explicit delete on release, not by TTL** — a hold is released when the cart is paid or
abandoned, and a TTL would make expiry silent. It carries `expiresAtEpoch` and is treated as
void past it, so a crashed checkout cannot hold a single-use coupon forever. A hold is advisory:
it prevents the ordinary double-spend race, and the authoritative single-use guarantee is the
conditional `COUPONREDEEM#` put below.

`COUPONREDEEM#<codeUpper>#<orderId>` is written with
`ConditionExpression: attribute_not_exists(couponKey)`. Keyed on **order**, not attempt: a retry
of one basket must not consume a second use, and `order_keys.new_order_id` only mints an `orderId`
after capture is verified. This row is terminal and is never deleted.

### 4.4 Index

    status-index   HASH status, RANGE createdAt

Sparse — only definition rows carry `status`, so counters, holds and redemption records never
enter it. Name follows the `<field>-index` convention live on PaymentsTable and
PaymentAttemptsTable. This serves the staff list of active coupons; `createdAt` keeps the query
bounded to a window instead of reading a whole low-cardinality status partition.

### 5.2 Commit, and where it is called from

`coupon_store.commit_redemption(table, *, code, order_id, customer_id)` is called **after**
capture is verified, from the finalization path, inside the same forward-only progression that
already records the order. It performs the conditional `COUPONREDEEM#` put, then the two atomic
`ADD`s (global `usageCount`, per-customer `uses`), then deletes the hold.

Order matters: the claim is irreversible and the counters are not, so the claim goes first. A
crash between the claim and the counters leaves a coupon that is correctly marked used for this
order with an undercounted total — recoverable by replay, because the claim is idempotent and the
`ADD`s are guarded by the claim having been newly won. The reverse order would double-count on
replay.

If `COUPONREDEEM#` already exists for this `(code, order_id)`, `commit_redemption` returns
`{"committed": False}` and touches nothing. That is the idempotency contract.

**Who may execute it, and the IAM consequence (closes HIGH-3).** `finalization.py` runs inside the
checkout/webhook function, not inside `wecare-coupons`. `wecare-checkout-role`'s inline policy
(`scripts/provision_checkout.py`) grants `dynamodb:GetItem, PutItem, UpdateItem` on exactly
`stack-wecare-digital-PaymentAttemptsTable` and `stack-wecare-digital-WixOrderIds`, so it cannot
touch `CouponsTable`. Both options were considered:

- **(a) additively extend `wecare-checkout-role`** with `GetItem, PutItem, UpdateItem, DeleteItem`
  scoped to the `CouponsTable` ARN;
- **(b) `lambda:InvokeFunction` into `wecare-coupons` synchronously** from finalization.

**Chosen: (a).** `wecare-checkout-role` is a *per-function* role, not the shared fleet role
`wecare-digital-lambda-role`, so the §6 objection — "a widening there grants every other function
the same access" — does not apply: this widening grants it to exactly one function, which is the
one that must do the write. (b) was rejected because it inserts a cross-function network call into
the middle of finalization, after capture is verified and before the order is complete; a
transient `lambda:Invoke` failure there turns a settled payment into
`NEEDS_RECONCILIATION` for a reason that has nothing to do with the payment. A DynamoDB
`UpdateItem` on a table in the same account is the smaller failure surface.

The role change is **SEAM-C3b** (§8), owned by whoever owns `provision_checkout.py`, with
test 52 asserting the policy names exactly the one new table ARN and grants no `Scan` and no
wildcard action. If the razorpay-webhook function turns out to be the finalizer instead, the same
extension applies to its role and only the ARN list in test 52 changes — which is why §11 asks the
owner to confirm which function finalizes.

#### 5.2.1 The grant must also enter the script's own IAM self-check (closes MEDIUM-18)

`provision_checkout.py` does not merely write the policy; it **verifies** it, by simulating a
fixed action list against a fixed table list. Both lists are hard-coded and neither would see the
new statement. Measured:

```python
scripts/provision_checkout.py:661   _SIMULATED_ACTIONS = ("dynamodb:GetItem", "dynamodb:PutItem",
                                                          "dynamodb:UpdateItem",
                                                          "dynamodb:ConditionCheckItem")
scripts/provision_checkout.py:785   tables = [f"...table/{PAYMENT_ATTEMPTS_TABLE}",
                                              f"...table/{COMMERCE_KEYS_TABLE}"]
# PAYMENT_ATTEMPTS_TABLE = "stack-wecare-digital-PaymentAttemptsTable"   (line 127)
# COMMERCE_KEYS_TABLE    = "stack-wecare-digital-WixOrderIds"            (line 128)
```

So a `DeleteItem` grant on a third table would be **granted but never measured**, by the script
whose stated job is measuring that role — and the simulation would keep reporting a clean verdict
even if the new statement were malformed. The script's own docstring is the argument against
leaving it: *"An unmeasured verdict is a problem too, not a pass… a run that measured nothing must
not be indistinguishable from one that measured everything and found nothing."*

**SEAM-C3b therefore has two halves, and the second is not optional:**

1. add the statement granting `dynamodb:GetItem, PutItem, UpdateItem, DeleteItem` on
   `table/stack-wecare-digital-CouponsTable`;
2. extend `_SIMULATED_ACTIONS` with `dynamodb:DeleteItem`, and extend the simulated `tables`
   list with the `CouponsTable` ARN.

`dynamodb:Query` is deliberately **not** added to either: the finalization path only ever touches
`COUPONREDEEM#`, `COUPONUSE#`, `COUPON#` and `COUPONHOLD#` rows by their exact partition key, so
it needs no `Query` and the staff `status-index` query runs in `wecare-coupons` under its own role
(§6). A grant nobody exercises is a grant nobody notices has gone wrong.

Note the asymmetry this introduces and why it is correct: adding `DeleteItem` to
`_SIMULATED_ACTIONS` means the simulation will now also be run against
`PaymentAttemptsTable` and `WixOrderIds`, where the expected verdict is **denied** —
`provision_checkout.py`'s existing policy comment says so outright (*"No DeleteItem: a checkout
never deletes a payment attempt or a reservation"*). That is a feature: the simulation then pins
both the new permission and the existing refusal. Test 52 asserts the simulation's action list
covers every action the policy grants, so the grant and the check cannot drift apart again.

### 5.3 Error handling, per operation

| Operation | Failure | Recoverable | Caller receives | Logged |
|---|---|---|---|---|
| Local claim put | `ConditionalCheckFailedException` | yes, terminal for this request | `409 CODE_ALREADY_EXISTS` | INFO, code in full |
| Local claim put | any other `ClientError` | fatal | `503`, no coupon created | ERROR, `type(exc).__name__` |
| Wix `Create Coupon` | non-2xx | yes | `202` + `wixMirrorState: PENDING_WIX` | WARN, HTTP status only |
| Wix `Create Coupon` | response has no `id` | yes | `202` + `PENDING_WIX` | WARN |
| Wix `Create Coupon` | duplicate code Wix-side | yes — **indistinguishable from any other failure**, so `202` + `PENDING_WIX` | WARN, HTTP status only |
| Wix `Get Coupon` probe on a `PENDING_WIX` row | finds a Wix coupon with our code and a different id | **needs reconciliation** | `409 WIX_CODE_CONFLICT` | ERROR |
| Wix `Update Coupon` (deactivate) | non-2xx | yes | `202` + local `INACTIVE` already applied | WARN, status only |
| Wix `Get Coupon` | non-2xx or `404` | yes | `200` + `wixMirrorState: PENDING_WIX` | WARN |
| `validate` | code unknown | n/a | `200 {verdict: UNKNOWN_CODE}` | INFO |
| `validate` | `wixMirrorState != MIRRORED` | yes | `200 {verdict: WIX_MIRROR_INCOMPLETE}` | WARN |
| `validate` | sub-rupee amount on the stored row | n/a, cannot occur | — | — |
| `hold` | hold held by another cart | yes | `409 HELD_BY_ANOTHER_CART` | INFO |
| `commit_redemption` | claim already exists | yes, idempotent | `{"committed": False}` | INFO |
| `commit_redemption` | claim put fails non-conditionally | **fatal, must not proceed** | raises | ERROR |

Deactivation applies locally **first** and then asks Wix, which is the opposite order from
creation, and deliberately: a coupon that is `INACTIVE` with us and still `active` in Wix is
refused by `validate` before `Add Coupon` is ever called, so the local state is the binding one.
The reverse order would leave a window in which we believe a coupon is live and Wix has already
switched it off.

A coupon that failed to mirror is `PENDING_WIX` and **not applicable** — `validate` refuses it.
That is fail-closed: a coupon Wix does not know about would be accepted by us and rejected by
`Add Coupon`, and the customer would see a discount that then vanished from the total.

A Wix error body is never surfaced or logged. `wix_ecom._request` already reduces an `HTTPError`
to a status-only message for exactly this reason (*"Status only. The body can carry buyer detail
and is not logged or surfaced."*), and that behaviour is relied on rather than re-implemented.

#### 5.3.1 `WIX_CODE_CONFLICT` cannot be detected from a `Create Coupon` failure (closes MEDIUM-9)

Revision 2 listed a duplicate-code refusal as an outcome distinct from a generic non-2xx, with
no detection mechanism and no cited error shape. **Re-fetched 2026-10-02, and the docs settle it
in the opposite direction from what revision 2 assumed.** The `Create Coupon` page's own OpenAPI
document declares:

```
"responses": {"200": {"$ref": ".../wix.coupons.api.v2.CreateCouponResponse"}}
"x-wix-docs": { ... "errors": [] ... }
```
https://dev.wix.com/docs/api-reference/business-solutions/coupons/coupons/create-a-coupon

**One response code and an empty `errors[]` array.** Wix documents no failure for this method at
all — no name, no `applicationCode`, no status. (The `COUPON_ALREADY_EXISTS` 428 entries in §1.2
belong to Cart V2 **Add Coupon**, which is a different service and a different condition: a
coupon already on *this cart*, not a code already on *the site*.) The uniqueness rule itself is
documented only as prose on `Specification.code` — *"Must be unique for all coupons on your
site"* — with nothing said about how a violation is reported.

Our own side cannot recover the status either. `wix_ecom._request` collapses every non-2xx into
one exception with no body and no structured code:

```python
amplify/functions/shared/lambda_utils/wix_ecom.py:106
    except urllib.error.HTTPError as error:
        # Status only. The body can carry buyer detail and is not logged or surfaced.
        raise WixEcomError(f"Wix eCom {method} {endpoint} returned HTTP {error.code}") from None
```

A `WixEcomError` therefore carries a status *inside a message string*, and `wix_ecom.py` is
read-only here, so no structured code can be added. Branching on a parsed message substring would
make a money decision depend on an exception's prose.

**Resolution, fail-closed and mechanical:**

1. **Every `Create Coupon` failure, of every status, leaves the row `PENDING_WIX`** and returns
   `202`. No status is special-cased, because no status is documented. A `PENDING_WIX` coupon is
   refused by `validate` (§5.3), so the worst case is a coupon that does not work — never a
   coupon that works differently from what was promised.
2. **`WIX_CODE_CONFLICT` is raised only by an explicit `Get Coupon` probe**, never inferred from
   a create failure. The probe runs on the reconciliation path for a `PENDING_WIX` row: retry
   `Create Coupon`; if it fails again, there is no Wix id to probe with, so the row stays
   `PENDING_WIX` and the staff list shows it. The conflict state is reachable only from the one
   case where we *do* hold a Wix id for our code and `Get Coupon` returns a coupon whose
   `specification.code` matches ours while its `id` is not our `wixCouponId` — which is a genuine
   two-owners-one-code disagreement and is the only thing a human needs to adjudicate.
3. `WIX_CODE_CONFLICT` is surfaced, never auto-resolved, because both resolutions (adopt the Wix
   coupon, or rename ours) change what a customer is promised.

The honest consequence is stated rather than hidden: **a duplicate code looks exactly like a
network timeout to us**, and both are retried the same way. That is acceptable precisely because
our own conditional put on `COUPON#<codeUpper>` (§2.1) is the first line of defence and has
already refused every duplicate *we* could have created. The only way to reach a Wix-side
duplicate is a coupon created in the Wix dashboard outside this system, which is an owner action
and is owner item 6.

Tests 37a and 37b cover both branches: a create failure of any status leaves `PENDING_WIX` and
never raises `WIX_CODE_CONFLICT`, and a `Get Coupon` probe returning a foreign id for our code
does raise it.

### 5.4 Validation of every external input

| Input | Rule | On failure |
|---|---|---|
| `code` | required, 1–20 chars, `^[A-Za-z0-9._-]+$`, NFKC-normalised | `400`, never forwarded to Wix |
| `name` | required, 1–100 chars after strip | `400` |
| `discountKind` | required, exactly one of the five | `400` |

| `percentOffBps` | integer, `0 < v ≤ 10000`, **`v % 100 == 0`** | `400` |

| `buyX` / `buyY` | integers `≥ 1` | `400` |
| `startTimeMs` | required, integer, `≥ 1000000000000` (Wix's documented minimum) | `400` |
| `expirationTimeMs` | optional, integer, `≥ 1000000000000`, strictly `> startTimeMs` | `400` |
| `usageLimit`, `limitPerCustomer` | optional, integer `≥ 1` | `400` |
| `discountedCycleCount` | refused outright — `pricingPlans` scope only, and scope is `stores` here | `400` |
| `scopeNamespace` | `"stores"` only in this change | `400` |
| `scopeGroupName` | optional, `product` or `collection` | `400` |
| `scopeEntityId` | required iff `scopeGroupName` present; GUID | `400` |
| scope / minimumSubtotal | at least one required, **unless** `FREE_SHIPPING`, which forbids scope | `400` |
| `tags` | optional, ≤ 100 items, each ≤ 255 chars | `400` |
| `currency` | `"INR"`, compared explicitly | `400` |
| `cartId`, `customerId` | GUID; `customerId` from the session, never the body | `400` / `403` |

The scope rule is transcribed from Wix's own prose rather than inferred, and `FREE_SHIPPING` is
the documented exception in both directions: it cannot carry a scope, and its `minimumSubtotal`
is optional. `type` is never sent, because the schema marks it read-only.

### 5.5 Invariants and who owns them

| Invariant | Owner | Why there |
|---|---|---|
| one coupon per normalised code | DynamoDB conditional put on `couponKey` | the only layer where concurrent writers serialise |
| global usage ≤ `usageLimit` | atomic `ADD` + `ConditionExpression` | a read-then-write loses a concurrent race |
| per-customer uses ≤ `limitPerCustomer` | atomic `ADD` on the `COUPONUSE#` row | same, and Wix cannot attribute it headlessly (§2.2) |
| one redemption per (code, order) | conditional `COUPONREDEEM#` put | idempotency must survive replay; a hold cannot |
| exactly one discount kind | `coupon_store` validation | must fail before Wix, since Wix's `type` is read-only |
| every Wix-bound amount is a whole-rupee `int` | `wix_coupons` conversion + the `% 100` validation | §4.2; the fields are JSON `number` and nothing documents a string |
| no numeric field is ever read from a Wix response | `wix_coupons` reads `id`, `active`, `type` only | `wix_ecom._request` has no `parse_float` (§4.2) |
| **the discount amount** | **Wix `Calculate Cart`** | one arithmetic (§2); we never compute a discount |
| `collection + fee + gst == total` | `CheckoutQuote.__post_init__` | already enforced; unchanged |
| no float on the money path | integer paise + integer division, floats refused by type | R6.1 |

The eighth row is the one to read twice. Our table records *what was promised*; it never computes
*what was deducted*.

## 9. The vocabulary gate, and why the list is split

`CONSULTING_FILES` in `tests/test_payment_vocabulary_at_decision_points.py` parametrises **two**
tests: `test_the_handler_imports_the_vocabulary_module`, which asserts the file binds
`lambda_utils.payment_status` under a given alias, and
`test_no_decision_compares_a_payment_word_raw`, the AST ban on a raw `'captured'` comparison.

Neither new handler has a payment-status decision. The coupon handler issues coupons and answers
eligibility; the gift-card handler issues cards; the gift-card ladder is its own module with its
own ranks. Adding them to `CONSULTING_FILES` would force an unused `payment_status` import purely
to satisfy a gate — which makes the gate dishonest, and an import nobody uses is the first thing a
later cleanup deletes, silently removing the file from the gate.

So the gate is split rather than stretched (closes MEDIUM-11). **This document owns the edit**, and
these are the exact tuples, all three of them, so the count is not ambiguous (closes MEDIUM-10):

```python

#: settlement ladder is its own module (gift_card_settlement) with its own ranks. Forcing an

    ("ecommerce/coupons/handler.py", None),

]


@pytest.mark.parametrize("relative,alias", CONSULTING_FILES + RAW_SCAN_ONLY_FILES)

    ...
```

`test_the_handler_imports_the_vocabulary_module` stays parametrised on `CONSULTING_FILES` alone,
so its six existing entries keep their meaning. `FORBIDDEN_RAW == {"captured"}` is unchanged, and
`test_paid_is_deliberately_not_in_the_forbidden_set` continues to pin the scope.

The SPI handler is included rather than omitted: it is the one new file that touches money on an

## 10. Constraints this design is bound by

- Integer INR paise only; no float anywhere. Rates are integer basis points. Conversion to Wix
  happens at the boundary by integer division, producing an `int` (§4.2), never a float and never
  a `Decimal` that `wix_ecom._request`'s `json.dumps` would reject.
- No numeric field is read back from any Wix coupon response, because `wix_ecom._request` parses
  with the default `json.loads` and a Wix `number` would arrive as a float (§4.2).
- Payment status decisions go through `payment_status.py`. The raw literal `'captured'` at a
  decision point is AST-banned; the new handlers join `RAW_SCAN_ONLY_FILES` (§9).
- A coupon code is **not** a secret and may be logged in full — the deliberate opposite of a
  gift-card code. Test 60 pins it so the asymmetry is not "tidied".
- No credential value in a command, argv, log, or logging expression. The Wix key is referenced by
  secret id and read lazily at request time; `secretsmanager get-secret-value` /
  `batch-get-secret-value` are never called from a shell or from `aws___run_script`.
- `WIX_CART_V2_ENABLED` / `CHECKOUT_INITIATION_ENABLED` and every live-send or initiation flag
  stay as they are. This change enables nothing.
- New Lambdas are **authored, not deployed**.
- One active architecture: website Razorpay Standard Checkout. No Wix-native PSP, no Velo
  backend, no `submitEvent` bridge, no second checkout mode. `Place Order` ("This endpoint may
  charge the customer") and `Get Checkout URL` are never called.
- `/stores/v3`, `/site-media/v1` and `/members/v1` are untouched. `/stores/v2/coupons` is a
  different surface from `/stores/v3` products and does not disturb it.
- No WAF, Security Hub, DNS, MX, MTA-STS, SPF, DMARC or Cognito change.
- `cart_v2.py`'s refusal of `memberships` and `subscriptionCharges` is preserved. Coupons do not
  touch `paymentSummary` at all.
