## High-level view

REV-1 is closed. The amended Authority cell names the incidental CI deploy and points at a
correction row rather than silently rewriting history, and that row's verification is load-bearing:
a live probe of `ANY /seo-tools` returning a structured `401` proves the handler executes, because
an import failure from a shared-layer change would surface as a 502 instead of valid JSON from the
auth gate.

REV-2's fix places the flag correctly — `credited = False` on the latch, set true only after the
balance returns, absence read as complete so a pre-flag latch is never re-credited, a lost latch
race still refusing. What it does not establish is the converse: `credited: False` does not mean
the credit has not landed. It also means "the credit landed and the flag write failed", and in that state the retry
re-drives an unconditional `ADD balancePaise`. The decision to replay money is taken from a read
(`original.get("credited") is not False`) and then executed without a condition binding it, which
is the read-modify-write on a money path that `docs/security.md` calls prohibited because it has
a window by construction.

`redeem()` has the identical shape and the same window. Its docstring opens "Move balance,
exactly once per `(codeHash, paymentAttemptId)`", and the claim row makes that true for a replay
that fails before the decrement. It is not true for a replay that fails between the decrement and
`_mark_settled`: the claim stays unsettled, the retry re-drives `_decrement`, and the card is
debited twice for one attempt. This one is worse on reachability, because `redeem` is on the
ordinary finalization path rather than behind the unprovisioned SPI.

The fix for both is the same invariant: the balance move and the marker flip must commit as one
atomic unit. `TransactWriteItems` is already the established answer in this repo for exactly this
class, and both items are in the same table so no role gains a new action.

### The marker says "not applied" in two different situations, and only one of them is safe to replay

The `credited` flag is written before the credit and set after it, so it can never claim a credit
landed when it did not. That direction is sound and is what the commit message argues. The
unsound direction is the one the retry depends on.

```python
balance_after = credit(table, code_hash=digest, amount_paise=amount, clock=clock)
_mark_credited(table, original_key, balance_after=balance_after, now=now)
```

Two separate writes to two separate items. `credit()` is `ADD balancePaise :amount` with no
idempotency key and no condition tying it to a void id, so it is replayable by construction.
`credited: False` therefore covers both "the credit never ran" and "the credit ran and the flag
write was throttled", and `void()` treats the two identically.

Reproduced by failing only the `SET credited = :true` write — strictly after the balance moved,
which is the window the committed test cannot reach because its fake aims the fault at
`ADD balancePaise :amount`:

```
after redeem           balancePaise = 10000
first void             raised GiftCardStoreUnavailable
balance after 1st void = 50000   credited = False     <- the money already came back
retry void             remainingBalancePaise = 90000
FINAL balancePaise     = 90000  (correct value is 50000)
```

The card was issued at 50000, redeemed 40000, and ends holding 90000 paise of liability nobody
paid for. The prior behaviour in this window was `AlreadyVoided` with the balance stranded —
a customer-side loss an operator could see and repair. This is a business-side loss that looks
like a successful void, and it is the double-credit the guard-before-credit ordering was
introduced to prevent, now reachable by retry instead of by race.

The three new tests all arm the fault at the credit itself, so they pin the recovery they were
written for and cannot see this. `test_a_void_latched_before_the_credited_flag_existed_is_never_re_credited`
is the closest, and it demonstrates the module already knows that re-driving an already-landed
credit hands the balance back twice — it just enforces that only for the absent-flag case.

### The same hole in `redeem`, on a path that is actually on the checkout route

```python
balance_after = _decrement(table, digest=digest, amount=amount, attempt=attempt, now=now)
_mark_settled(table, claim_row_key, balance_after=balance_after, now=now)
```

`_decrement` is conditioned on `balancePaise >= :amount`, which stops an overdraw but does not
stop a second deduction while funds remain. Failing only `SET settled = :true`:

```
first redeem  raised GiftCardStoreUnavailable
balance after 1st = 30000 (expected 30000)      <- the debit landed
retry redeem  remainingBalancePaise = 10000
FINAL balance = 10000  (correct value is 30000)
```

20000 paise taken twice under one `paymentAttemptId`. The claim row's comment says the re-drive is
safe because "the amount is already known to match, by the conflict check above" — that check
proves the two requests agree on the figure, not that the figure has not already been applied.

This is the higher-reachability of the two. `void()` is only callable from the SPI's `/v1/void`,
which needs a `transactionId` Wix can only learn from a `/v1/redeem` response that §1.3 predicts
never happens. `redeem()` is the gift-card leg of ordinary finalization.

### What the fix has to guarantee

Not "retry more carefully" — the balance move and the applied-marker must be one atomic commit, so
that no interleaving can leave money moved and the marker unset. Two shapes fit the repo:

`TransactWriteItems` over the card row (`ADD balancePaise`) and the evidence row
(`SET credited = :true` / `SET settled = :true` under `attribute_exists` plus the current-value
condition). Both items live in `GiftCardsTable`, so no role gains an action it does not already
hold. `docs/security.md` already states the principle for the customer-signup path in these words:
read-then-write is prohibited, it has a window by construction.

Or fold the marker into the money write itself — one `UpdateItem` on the card row with
`ADD balancePaise :amount SET appliedVoids.#void = :at` and
`attribute_not_exists(appliedVoids.#void)` in the condition, which makes the money move its own
idempotency record on one item. Bounded by the card's lifetime redemption count against the
400 KB item limit, which for a gift card is not a real constraint.

One thing to check before choosing transactions: `provision_checkout.py::_package_needs_transactions`
walks the checkout package's import closure for `transact_write_items` and reports a required
`dynamodb:ConditionCheckItem` grant. `finalization.py` is named as the owner of SEAM-G5, so
`gift_card_store` may land inside that closure — confirm whether the grant report changes before
assuming the IAM side is untouched.
