# Phone normalisation fix — review iteration 3

Review pass 3 over commits `456b5716`, `f8a73fb0` and `892e2d63` on `stack`. The five findings from
iteration 2 are all genuinely closed: the trigger's separator predicate was replaced with
`not ch.isspace()`, the masked-destination test now takes `monkeypatch` instead of assigning onto a
`scope='module'` fixture, `_LOG_CALL_RE` is gone, the tautological assertion became a length check,
and the doc's three false deploy claims were replaced with measured CloudTrail evidence, byte-exact
digest attribution and retrospective rollback targets.

One new finding, and it is the same class of defect iteration 2 raised. `892e2d63` set out to "make
the predicate the same predicate" and verified the whitespace class exhaustively across all
0x110000 codepoints. There are two predicates in that function, and only one of them was made
identical. The digit filter still disagrees on 128 codepoints: the canonical function strips with
`re.sub(r"\D", …)` (Unicode category Nd) while the trigger keeps `ch.isdigit()` (Nd **plus**
Numeric_Type=Digit, so `²³¹`, Ethiopic numerals and 122 others). The drift-agreement table cannot
see it, for exactly the reason the table's own comment gives about the previous divergence.

**Watch for:** the digit-predicate divergence between the two phone implementations (confirmed, 128
codepoints, measured); and the strict function returning non-ASCII digits as "E.164" at the door
that reserves the identity (confirmed, `+91933099440٠` is accepted and is a different Cognito
`Username` from `+919330994400`). Both are closed by the same one-line change in each file.

**Verdict**: NEEDS_CHANGES

## High-level view

The ordering that is the whole fix is correct. `normalize_phone_preserving_country` branches on
`+` / `00` against `compact`, which is separator-stripped but marker-preserving, and only then calls
`re.sub(r"\D", …)`. Nothing resembling a wrapper around `normalize_phone` is present. AST extraction
confirms `normalize_phone`, `build_customer`, `is_indian_mobile`, `DEFAULT_COUNTRY_CODE` and
`_INDIAN_MOBILE_RE` byte-identical to `456b5716~1`, `normalize_phone` at 1896 bytes either side, and
the `customer.py` diff is `+120 -0`.

Three guards sit on the anti-delegation property, not one: a monkeypatch tripwire over both the `+`
and the `00` input, an AST walk over the new body for calls to `normalize_phone` and references to
the two India symbols, and a statement-ordering test requiring the marker branch before every `\D`
strip. The ordering test is the one carrying the weight, since a function can avoid all three
symbols and still strip digits first. One soft edge: it locates the strip by the literal `\D`, so the
rewrite issue 1 recommends would need the pattern widened with it.

Exactly four entry points are wired, confirmed by grep across `amplify/**/*.py`. `build_customer`,
`validation.py::normalize_phone`, `outbound-whatsapp`, `sinch_rcs`, `checkout`, `customer_cart`,
`initiation`, `address.py` and `crm` are untouched, and the trigger still imports nothing from
`lambda_utils`.

One shared case table asserted on both implementations is the only mechanism holding them together,
given the standalone packaging — which is why a predicate that agrees by coincidence rather than by
construction is the thing to look hardest at. The separator predicate is now equivalent by
construction. The digit predicate is not, and the divergence lands on the value used as the WhatsApp
`to` field and as the per-phone throttle key.

The no-store work reaches `otp_throttle.throttled_response`, which does not go through
`cors_response` and would otherwise have been the one uncovered path. `response.py` is unmodified,
and a test asserts it contains no `Cache-Control` at all, pinning the negative decision at
`core/contacts/handler.py:285` so it cannot be tidied into the shared builder later.

Finding 3 is report-only with `simulate-principal-policy` output on both roles, the verbatim
`DynamoDB` statement, the proposed explicit-Deny policy, the rejected wildcard-narrowing alternative
and a one-call rollback. No IAM write was attempted.

The deploy that iteration 2 uncovered is recorded with the part that reflects worst on the author
left in: rollback targets were captured after the alias moved, which breaches the `A3_PRODUCTION`
precondition, and the doc says so in those words. The original false sentence is preserved as a
correction block rather than silently replaced.

### The digit predicate is the second half of a fix that was only half applied

`892e2d63`'s comment in the trigger is precise about what it verified:

```python
# `not ch.isspace()` rather than an explicit `" \t"` set, because the canonical
# implementation compacts with `re.sub(r"[\s\-().]", "", text)` and `\s` matches every
# codepoint for which `str.isspace()` is true - verified exhaustively across all
# 0x110000 codepoints, zero disagreements.
```

Reproduced and confirmed: `re.compile(r"\s").fullmatch(chr(cp))` and `chr(cp).isspace()` agree on
all 1,114,112 codepoints. That claim is sound.

Four lines further down the same function the other predicate is spelled differently and is **not**
equivalent:

```python
# customer.py:258 (canonical)
digits = re.sub(r"\D", "", rest)

# customer-whatsapp-auth/handler.py:217 (trigger)
digits = "".join(ch for ch in rest if ch.isdigit())
```

`re`'s `\d` matches Unicode category Nd. `str.isdigit()` matches Nd **and** anything carrying
Numeric_Type=Digit. Measured: 128 codepoints disagree, beginning `²` (U+00B2), `³`, `¹`, then the
Ethiopic numerals from U+1369.

Measured against the two live implementations:

```
'+65²91234567'    canonical: 6591234567     trigger: 65²91234567     DISAGREE
'+919330994400²'  canonical: 919330994400   trigger: 919330994400²   DISAGREE
'+91²09330994400' canonical: 919330994400   trigger: 91²09330994400  DISAGREE
```

The trigger's docstring says it returns "WhatsApp's digits-only E.164 destination". It returns a
string containing a non-digit. That output is used three ways at lines 231, 238 and 386: as the
`_consume_send_budget` key, as the `"to"` field of the WhatsApp send, and in the sign-in path. The
dangerous direction here is availability rather than misdelivery — Meta rejects the `to` value, so
the OTP fails visibly instead of reaching a stranger — but a throttle key that changes with an
invisible character is a budget bypass, and the function's stated contract is broken either way.

What makes this blocking rather than a nit is the mechanism, not the reachability. The drift table is
the only thing holding the two copies together, and the table's own comment explains why it cannot
catch a predicate divergence:

> a row in this table cannot see a separator-predicate divergence ... it still produces
> `6591234567` for both rows below, because the trailing `isdigit()` filter discards whatever the
> compaction left behind.

That paragraph describes the digit filter as the thing that *hides* divergences while leaving the
digit filter itself as a second, unverified spelling. `test_the_two_implementations_agree_on_refusal_too`
covers three inputs and none of them is a numeric-but-not-decimal character.

Today's practical exposure is narrow: the value reaching `_normalise_phone` is the Cognito
`phone_number` attribute, and Cognito validates that format. The docstring states that assumption
explicitly. Nothing enforces it, and the function is live in production as version 11.

The trigger does not currently import `re`, but `re` is stdlib and adding it does not affect
`standalone=True` packaging. Either spelling closes it, provided both sides change together:
`re.sub(r"[^0-9]", "", rest)` canonically with `ch in "0123456789"` in the trigger is exact by
construction and needs no import at all.

### Non-ASCII digits reach the identity reservation

Measured on the new strict function:

```
'+٩٣٣٠٩٩٤٤٠٠٠٠'   -> '+٩٣٣٠٩٩٤٤٠٠٠٠'
'+91933099440٠'    -> '+91933099440٠'
'+919330994400'    -> '+919330994400'
```

Arabic-Indic digits are category Nd, so `\D` does not strip them, the 8..15 bound counts them, and
the function returns them as E.164. `normalize_phone` behaves the same way, so this is not a
regression in the lenient function and its frozen snapshot must not change — but
`normalize_phone_preserving_country` is new code, and it sits at `registration.complete`, which
writes `normalizedPhone` and the Cognito `Username` from this value and enforces uniqueness on it.

`+919330994400` and `+91933099440٠` are therefore two distinct identities that a human reads as one
number. That is the same failure the headline defect produced — the wrong identity reserved,
permanently, with no later correction — arriving through a different door. A direct API caller is
the reachable path, which is the caller the docstring already acknowledges when it explains why bare
national digits are refused rather than defaulted.

Restricting both implementations to ASCII `0-9` closes this and the drift finding in one change. No
row of `PRESERVED` or `LEGACY_SNAPSHOT` is affected, since every fixture there is ASCII.

Iteration 2's three deploy findings are closed without the easy move of deleting the false sentence.
The attribution does not rest on timing: `wecare-customer-whatsapp-auth` is packaged with one

rebuilding from `b1833c22` reproduces version 11's, and the `PublishVersion` description names the

The `seo-tools-deploy.yml` path is recorded with the boundary that makes it actionable: the workflow

way and `identity/customer.py` and `identity/registration.py` did not. Flagged for
`lambda-snapstart-deploy.md`, which documents only the manual path.

Plan §0.4 argued the trigger and registration fixes must land together; production inverted it. The
trigger is deployed and strict while `wecare-customer-registration` and `wecare-email-verification`
do not exist in the account. The doc records that as the safe half of the asymmetry and retires the
premise rather than re-quoting it.

Worth holding alongside issue 1: live version 11 carries the iteration-2 separator bug, because the
`not ch.isspace()` correction is source-only. Whatever ships next to that function will therefore
carry both predicate fixes at once, which is an argument for fixing the digit predicate now rather
than in a follow-up.

### The throttle axis change, for the record

`email-verification` now normalises the phone before it becomes a throttle subject, and falls back
to the email on any `InvalidPhoneNumber` — which `MissingCountryCode` subclasses. One behavioural
consequence worth stating rather than fixing: a bare national number used to get its own bucket and
now lands on the email bucket, so the same bare number paired with N emails gets N buckets on the
phone axis. It is bounded by the per-IP axis in `otp_throttle.check_and_consume`, the subject is
SHA-256 hashed before it becomes a key, and this endpoint sends codes to the email rather than the
phone, so keying on the email is the more defensible axis. Not a finding; noted so it is a decision
rather than an accident.
