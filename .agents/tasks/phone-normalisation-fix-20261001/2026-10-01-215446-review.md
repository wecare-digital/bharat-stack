## High-level view

The predicate work is now exact rather than coincidental. `[^0-9]` and `ch in "0123456789"` are the
same set by construction, measured at 0 disagreements across `range(0x110000)`, which is the same
standard iteration 2 applied to the separator pair (also re-verified at 0 here). The two
implementations cannot share code — the trigger is packaged `standalone=True` with `Layers: null` —
so a shared case table asserted against both is the only thing holding them together, and it now
contains rows that fail the moment the predicates diverge.

The ASCII restriction also closes the second finding: an Arabic-Indic digit is category Nd, so `\D`
left it in place and it was returned inside the E.164 that `registration.complete` writes as
`normalizedPhone` and the Cognito `Username`. The new test asserts the shape of the output rather
than one codepoint, which is the right assertion for "a non-digit reached the identity".

The ordering that is the whole fix is intact and I checked it by mutation, not by reading. I built an
in-memory `customer.py` in which the strict function is the classic delegating wrapper around
`normalize_phone`, and all three guards reject it: the monkeypatch tripwire (which covers both the
`+` and the `00` input), the AST delegation guard, and the statement-ordering guard, which now
recognises both `\D` and `[^0-9]` by explicit enumeration rather than by a looser `re.sub` match that
would have caught the separator compaction and inverted the assertion.

`normalize_phone` is untouched. AST extraction against `456b5716~1` gives identical source segments
and sha256 for `normalize_phone`, `build_customer`, `is_indian_mobile`, `DEFAULT_COUNTRY_CODE` and
`_INDIAN_MOBILE_RE`, with five names added and none removed. `LEGACY_SNAPSHOT` still pins the
corrupting legacy outputs, including `+91 09330994400 -> +9109330994400`.

Scope is clean. The union of files across all seven task commits is twelve, and it contains nothing
under `src/`, no `response.py`, no `validation.py`, no `outbound-whatsapp`, `sinch_rcs`, `checkout`,
`customer_cart`, `initiation`, `address.py` or `crm`, nothing under `docs/execution/snapshots/`, and
one new doc. The strict normaliser has exactly three importing call sites plus the in-place trigger
copy. Every builder return in both auth handlers is wrapped (5 and 15), and `response.py` contains no
`Cache-Control` at all.

Finding 3 is still report-only: `list-role-policies` on `wecare-digital-lambda-role` returns the same
sixteen inline policies with no session-table deny among them, so no IAM write was attempted. No new
production mutation since iteration 3 either — `wecare-customer-whatsapp-auth:live` is still version

The doc regression is the only thing standing between this and approval, and it is a one-table edit.

### The doc stopped obeying its own masking rule

Line 27, unchanged since the doc was written:

> **Phone numbers in this document are masked to the last four digits**, per the repo's logging rule.

The main reproduction table honours it, and does so without losing the mechanism, because the
mechanism is the digit *count*:

```
| `+65 ···4567` Singapore            | 10 | `+91` + all 10 → **wrong country** | `+65` preserved ✅ |
| `+91 0···4400` India with a trunk zero | 13 | **stuck trunk zero**, 13 digits out | one zero stripped ✅ |
```

The section `7d1421b4` added does not:

```
| `+65<U+00B2>91234567`   | `+6591234567`   | **`65<U+00B2>91234567`**   |
| `+919330994400<U+00B2>` | `+919330994400` | **`919330994400<U+00B2>`** |
| `+91<U+00B2>09330994400`| `+919330994400` | **`91<U+00B2>09330994400`**|
```

Measured per revision, scanning for 7+ digit runs and discarding the account id, the CI run ids and
the date stamps:

```
f8a73fb0  []
ac1b0c37  []
ed9fa198  []
892e2d63  []
7d1421b4  ['09330994400', '6591234567', '91234567', '91933099440', '919330994400']
```

So this is a regression introduced by the commit under review, not an inherited condition — which is
also why iteration 3's scan of the same doc reported only account ids, API versions and run ids.

`919330994400` is not a fixture. `amplify/functions/shared/lambda_utils/notifications/events.py:98`
sets `_DEFAULT_BUSINESS_NUMBERS = "+919330994400,+919903300044,+918031830030"` and line 95 records it
as "WABA1 / primary WhatsApp Calling". A business number is public-facing, so the disclosure harm
here is low — what makes it worth fixing is that the constraint was explicit in FEAT-002's acceptance
criteria, the doc asserts compliance with it in its own second paragraph, and `892e2d63` went to the
trouble of rewriting a sentence to avoid printing two Singapore spellings. A document that states a
masking rule and then breaks it teaches the next reader that the rule is decorative.

The fix costs nothing, because the superscript rows carry their meaning in the position of the
non-decimal character, not in the digits around it: `+65 ···<U+00B2>···4567` with "10 digits" beside
it makes exactly the same point, and the trunk-zero row's point is that the superscript sits between
`91` and the `0`.

The test fixtures are a separate matter and are fine as they are — `tests/` is where a case table
belongs, and the drift rows have to be literal to be assertable.

### The two predicates are now the same predicate

Enumerated rather than argued, for both pairs:

```
re.sub(r'[^0-9]', ...)  vs  ch in "0123456789"        0 disagreements over 0x110000
re.sub(r'[\s\-().]',..) vs  isspace() or ch in "-()."  0 disagreements over 0x110000
```

The second is iteration 2's claim re-measured, since the first change could have perturbed it.

The trigger keeps its own spelling rather than importing `re`, and the comment says why: the file is
`standalone=True`, so an import is a packaging question rather than a style question. That is the
right instinct even though `re` is stdlib — the deployed function has `Layers: null` and the deploy
map entry is not an owned path.

One residual asymmetry, deliberate and harmless: the canonical function raises
`InvalidPhoneNumber("phone number contains no digits")` where the trigger falls through to its
8..15 bound. Both refuse, and `test_the_two_implementations_agree_on_refusal_too` asserts refusal
rather than a message, so the drift table does not care which exception text arrives.

### The anti-delegation guards, verified by mutation

Replacing the strict function body with the delegating wrapper the review brief names as the defect
in a new coat:

```
test_the_strict_function_never_routes_through_the_inferring_one   FAILED
test_the_strict_function_body_cannot_reach_the_india_default      FAILED
test_the_marker_branch_precedes_every_digit_strip                 FAILED
```

The third one is the one that matters most, since a function can avoid `normalize_phone`,
`DEFAULT_COUNTRY_CODE` and `_INDIAN_MOBILE_RE` and still strip digits before reading the marker. Its
widening in this commit is correctly conservative: it enumerates `\D` and `[^0-9]` instead of
matching any `re.sub`, because the separator compaction is also an `re.sub` and it runs *before* the
marker branch by design, so a looser match would have inverted the assertion into one that passes on
a broken function.
