## High-level view

The root cause is proven rather than argued. `customer_auth.authenticate()` read `custom:customer_id`, an
attribute absent from pool `us-east-1_46ULYuukt`'s schema — `DescribeUserPool` reports exactly one custom
attribute, `custom:partner_waba_id` — so the read returned `''` for every token ever issued and the
function raised for 100% of customers. Four `{"event":"customer_auth_no_customer_id"}` WARNING lines at
02:44:00.283Z, 02:45:11.732Z, 05:33:55.013Z and 06:02:13.625Z on the `[5]` alias streams are the owner's
own confirm attempts, and `CustomerSessionsTable` at 0 items shows the exchange had never once succeeded.
CloudWatch looked clean because the handler returns 401 as a normal return, so the only line is a WARNING.

The reproduction is real-browser and labelled. Chrome 154.0.8037.93 headless over CDP against the real
`next build --webpack` export, three responses canned because a genuine code needs the owner's handset:
`InitiateAuth`, `RespondToAuthChallenge`, and the session endpoint at 401 or 200. Pre-fix renders exactly
`Try again shortly.` and discards a valid token; post-fix navigates to `/cart/` with the token stored.
The observed statuses are 200, 200, 401 — no 5xx anywhere — which settles that `messageForAuthError`'s
name-based catch-all fired and not `messageForVerifyRejection`'s `status >= 500` branch, the ambiguity
the brief flagged.

The fix matches the cause on both sides. `customer_id_from_attributes` makes the Cognito `sub` the single
authority, deliberately not a fallback, with the reasoning and the five empty-table measurements recorded
in the docstring; `submitOtp` now stores the session before the exchange and degrades a refused exchange
to `remembered: false` instead of throwing. No production code reads `custom:customer_id` any more.

Defect 2's final shape came from upstream, not this branch, and the branch says so. `2f742ec6` fixed the
styled-jsx scoping that produced the run-together rendering; `1c847107` then retired the two-tone pill on
owner instruction, so the confirm button is now one `pill-action` span reading exactly `Confirm code`.
`SignInMessages.test.tsx` pins that at the page level — `.pill-label` null, `.pill-action` textContent
exactly `Confirm code`, no `aria-label`, no `aria-hidden` — which is the non-concatenation assertion the
brief asked for. This branch's contribution to defect 2 is the independent diagnosis, the build-output
scoping test, and option C, which upstream has since superseded.

The deliberate structures are intact. `MSG` is still a named table sourcing all seven approved strings
from `lib/signInMessages`, with `NOT_ON_WHATSAPP` present and still deliberately unwired; all three of
`messageForAuthError`, `messageForVerifyRejection` and `messageForHttpStatus` are unchanged.
`SignInMessages.test.tsx` keeps its exact-copy pins and its assertion that the page imports the constants
by name, and adds the 401 and 200 exchange cases driving the real `submitOtp`.

Hard constraints hold. No live-send flag, no `update-user-pool` or `add-custom-attributes`, no credential
read, no masking change — the one `*******0044` in the diff is an existing mask in a test fixture. The
deploy that made the server fix live was another session's, with owner authorization recorded in the
matrix, and it went shared-layer-first, which is the sequencing iteration 2's finding 7 asked for.

The five Python failures are reported separately and left alone, and the brief's premise is corrected
rather than quietly inherited: the 5 it named were fixed upstream by `c7afae00`, and the 5 now failing

### The conflict, and why neither side is a safe resolution

`git merge-tree --write-tree --name-only HEAD origin/stack` names exactly one path:

```
src/test/PillButtonBuildScope.test.ts
CONFLICT (content): Merge conflict in src/test/PillButtonBuildScope.test.ts
```

Two edits to the same regions, an hour apart, with neither author aware of the other. `47daedd9` replaced
the docblock's one-line skip claim with the three-state table, added `readPage()`, and swapped
`const present = existsSync( PAGE ); const run = present ? it : it.skip` for a `built = existsSync( OUT )`
gate whose skip titles carry the build command. `1c847107`, in the same commit that retired the two-tone
button, left that machinery alone and rewrote the third case instead:

```
-  run( 'scopes BOTH segments of the two-segment sign-in pill specifically', () => {
+  run( 'scopes the sign-in pill label specifically, not just the outer control', () => {
...
-    for ( const segment of [ 'pill-label', 'pill-action' ] as const ) {
+    for ( const segment of [ 'pill-action' ] as const ) {
```

On `origin/stack`, `PillButton` renders one span; `pill-label` survives there only inside a historical
comment. So the branch's loop would assert `no element carries .pill-label in the built page` against a
component that cannot emit it, and CI would catch it after the merge rather than before —
`build-test.yml` builds before `npx vitest run`, so the case runs rather than skips.

The reverse resolution is not free either. `origin/stack` still carries the defect iteration 2 raised as
finding 5: `it( 'has a built page to inspect', … )` is a plain `it` asserting `existsSync( PAGE )`, so
`npx vitest run` on a tree with no `out/` goes red over an artifact no other test needs. That is the one
frontend improvement this delta still has to offer, and discarding it leaves the file as it was when the
finding was written.

### The refresh-owner test is load-bearing, not decorative

`test_a_refresh_token_from_another_customer_is_refused_and_files_no_session` closes the half of finding 6
that upstream's comment-only `07e2c016` left open. It pairs a valid access token for `sub-1234` with a
refresh token redeeming to `sub-9999`, using a `GetUser` fake keyed on the token so the handler's two
`authenticate()` calls genuinely see different users, and both tokens carry
`_customer_auth.CUSTOMER_POOL_ISSUER` so the issuer pin is not what refuses them:

```python
class PerTokenCognito:
    def get_user(self, AccessToken=None):
        attributes = other if AccessToken == renewed_token else REAL_POOL_ATTRIBUTES
        return {'Username': '+919330994400', 'UserAttributes': attributes}
```

It asserts 401 `VERIFICATION_REQUIRED` and `store.rows == {}`, so the failure is closed rather than
merely unsuccessful. The revert check in the commit message — neutralising the comparison fails it with
`200 == 401` — is what rules out a vacuous pass, and it states the consequence plainly: without that line
the endpoint hands out a session over the victim's `sub`.

The decision not to re-establish a second independent field is recorded in the test docstring and is the
right call: `identity.phone` is the only candidate and it is mutable Cognito state, so a change landing
between the two `GetUser` calls would refuse a legitimate sign-in — the same failure class this task
exists to remove.

### Which classifier fired, settled by measurement

The brief warned that `MSG.TRY_LATER` is reachable two ways and the diagnosis had to say which. The
answer comes from reverting the client fix, rebuilding, and re-running the same browser scenario, not
from reading the code: pre-fix renders `Try again shortly.` and stays on `/account/sign-in/`, and the
only non-200 in the whole flow is the 401, so `messageForVerifyRejection`'s `status >= 500` branch cannot
have fired. A bare `new Error(…)` carries `name === 'Error'`, which matches none of
`TooManyRequests|LimitExceeded|TooManyFailedAttempts`,
`ExpiredCode|NotAuthorized|ExpiredToken|ResourceNotFound` or `CodeMismatch`.

Two harness details make the measurement trustworthy rather than incidental. The message renders into the
page's error region, not via `alert()`, so a driver watching only for a JS dialog sees nothing and reads
as a pass. And each scenario ran in its own Chrome profile, because `sign-in.tsx:223` redirects an
already-signed-in visitor straight to `/cart/` — a reused tab never reaches the form on a second pass and
silently measures `/cart/` twice.
