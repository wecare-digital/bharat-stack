# Legacy invoice payment claim made reconcilable to close the stranded-claim window (v2)

This follow-up addresses the one actionable issue from the v1 review: the legacy path's one-time `PROVIDERPAYMENT#<payment_id>` claim was taken inside `_verified_legacy_invoice` *before* `_mark_invoice_paid_by_reference` ran, so a settle that then no-opped (row vanished, became ambiguous, or write errored) burned the claim with no settled row behind it and stranded a legitimate payment forever. The fix makes the claim reconcilable: `_mark_invoice_paid_by_reference` now returns a truthful settled/not-settled verdict, `_verified_legacy_invoice` returns the claimed invoice id, and `_handle_payment_captured`'s legacy branch settles first and releases the claim via a new conditional `release_legacy_invoice_payment_claim` only when nothing settled. The v1 dead-helper annotation (Issue 2) and the fail-closed binding justification (Issue 3) are also handled.

Watch for: nothing blocking. The release is conditional on the row still being this payment's `LEGACY_INVOICE_PAYMENT_CLAIM` for this invoice, so it cannot remove a commerce `PROVIDER_PAYMENT_CLAIM` or a re-bound claim (confirmed); it runs only after the settle reports not-settled, so no double-settle is reachable (confirmed). The verified-commerce branch is byte-for-byte unchanged (confirmed).

**Verdict**: APPROVED

## High-level view

The money-safety argument rests on one ordering invariant: on the legacy path the settle now runs first, and the release fires only when `_mark_invoice_paid_by_reference` reports no row settled. Because no invoice is paid for this payment anywhere at release time, dropping the claim cannot enable a double-settle — it only re-opens the one legitimate settlement for a later Razorpay redelivery.

The release's safety against collateral damage is carried entirely by its conditional delete. The condition requires `kind=LEGACY_INVOICE_PAYMENT_CLAIM AND invoiceIdRef=<invoice_id> AND providerTransactionId=<payment_id>`, so it can never remove a commerce `PROVIDER_PAYMENT_CLAIM` (which writes `kind=PROVIDER_PAYMENT_CLAIM`) sharing the `PROVIDERPAYMENT#` namespace, nor a claim another worker re-bound to a different invoice. A lost condition is a no-op `False`; only a non-conditional error raises.

The `_mark_invoice_paid_by_reference` return contract is the other load-bearing piece. It returns `True` whenever a paid row exists for the reference — including the "already paid" and `ConditionalCheckFailed` branches — and `False` only when nothing settled (no row, ambiguous, or storage error). The "already paid ⇒ True" mapping is what stops a redelivery arriving after a real settle from releasing a legitimately held claim.

The prior-pass defenses are untouched. R1/C1's `UNKNOWN_REFERENCE`-only fall-through, R2's binding + one-time claim + single-row conditional settlement, and the verified-commerce store→settle→post-payment ordering are all unchanged; the legacy branch only adds a release-on-failure. The v1 dead inbound helpers are now annotated RETIRED (comment-only), and the fail-closed binding posture is documented as intended rather than relaxed.

### Settle-first-then-release ordering closes the window without opening a new one

The legacy branch in `_handle_payment_captured` now reads:

```python
if legacy_invoice_verified:
    if not _mark_invoice_paid_by_reference(reference_id, request_id, payment_id):
        _release_legacy_invoice_payment_claim(payment_id, legacy_invoice_id, request_id)
        _quarantine_unverified_capture(reference_id, payment_id, outcome, request_id)
        return
    _store_payment_record(payment, 'captured', request_id)
else:
    _store_payment_record(payment, 'captured', request_id)
    _mark_invoice_paid_by_reference(reference_id, request_id, payment_id)
```

The release is reached only through the `not _mark_invoice_paid_by_reference(...)` arm, i.e. only after the settle has reported no paid row for this reference. At that point no invoice is paid anywhere for this payment, so releasing the claim cannot enable a second settlement of a different invoice — it only lets the one legitimate settlement happen on a later redelivery, which re-claims and re-attempts. If the ambiguity or vanish persists on redelivery it quarantines again, so the behavior is idempotent. The `_store_payment_record` call on the legacy success arm now runs *after* a confirmed settle rather than unconditionally, which is the correct tightening: a stranded delivery writes no captured record (the test asserts `store.assert_not_called()`).

### The settle verdict must stay truthful, and it does

The release is only money-safe if `_mark_invoice_paid_by_reference` never returns `True` without a paid row behind it, and never returns `False` when one exists. The branches map correctly: no-row and ambiguous return `False`; the fresh conditional update returns `True`; the "already paid" short-circuit and the `ConditionalCheckFailed` arm both return `True` (a paid row exists, just not written by this call); and the outer `except` returns `False` (a storage error means settlement is unconfirmed, so the caller should release rather than strand). The "already paid ⇒ True" direction is the subtle one and it is correct: a redelivery arriving after a genuine earlier settle must *keep* the held claim, not release it, or a subsequent cross-reference replay would find the claim gone. `test_release_is_money_safe_when_a_row_actually_settled` pins the settled-row-keeps-claim case.

### The conditional delete cannot touch a commerce or re-bound claim

`release_legacy_invoice_payment_claim` deletes `PROVIDERPAYMENT#<payment_id>` under `kind = LEGACY_INVOICE_PAYMENT_CLAIM AND invoiceIdRef = <invoice_id> AND providerTransactionId = <payment_id>`. The commerce claim path writes `kind="PROVIDER_PAYMENT_CLAIM"`, so the `kind` predicate alone makes a commerce claim unremovable even though both share the `PROVIDERPAYMENT#` key space; `test_release_never_removes_a_commerce_provider_payment_claim` drives exactly this and asserts the commerce claim survives. The `invoiceIdRef` predicate bounds the release to the invoice the claim named, so a claim another worker re-bound to a different invoice is a no-op release (`test_release_only_removes_the_matching_invoice_claim`). A lost condition returns `False`; only a non-conditional error raises `OrderIdentityUnavailable`, so a throttle is never mistaken for a successful release. The handler wrapper `_release_legacy_invoice_payment_claim` swallows that raise, logs by type, and still quarantines — a failed release leaves the claim in place, i.e. degrades to the pre-fix behavior rather than to anything worse.

### Prior-pass defenses verified intact

The replay and ambiguity defenses are unchanged because the claim-acquisition side (`_verified_legacy_invoice` → `claim_legacy_invoice_payment`) is untouched except for returning the invoice id instead of a bare bool: a same-payment-different-reference replay still finds the claim held and settles nothing, and a one-payment-two-invoices reference still trips the `Limit=2` ambiguity guard and settles none. The release only ever runs when the settle found nothing to settle, so it never fires on a held-and-backed claim. The verified-commerce branch keeps its original store→settle→post-payment order verbatim; `test_razorpay_webhook_captured_gating.py` and `test_payment_reconciliation_safety.py` pass unchanged (31 passed). The R1/C1 `outcome_kind == UNKNOWN_REFERENCE` gate and R2 binding are not in the diff's edit surface.

### v1 Issue 2 and Issue 3 disposition

Issue 2 (dead financial helpers in the inbound handler) is handled by comment-only RETIRED banners on `_mark_invoice_paid_by_reference`, `_generate_invoice_for_captured_payment`, and `_check_and_notify_balance_due`, each pointing at the Razorpay webhook as the single authoritative producer and warning against re-wiring into a money path. The helpers stay defined (not deleted) so the env-var/code contract is not silently removed. No behavioral change, which matches the v1 recommendation. Issue 3 (binding requires a stored provider id on legacy rows) is deliberately unchanged: refusing an unbound invoice is the money-safe R2 posture, an unbound capture lands in durable quarantine for human binding rather than being lost, and the correct remediation for a corpus lacking provider ids is a one-time backfill, not relaxing the gate.

### Test coverage

The +4 group-(e) cases cover the previously untested stranded-claim window from both directions: a settle armed to error releases the claim and a redelivery then settles exactly once; a real settle keeps the claim; the release never removes a commerce claim; and the release is bound to the named invoice (wrong-invoice release is a no-op). The fake was taught `delete_item` with the same conditional-expression evaluator used for conditional updates, including the `<>` form, so the conditional delete is exercised rather than stubbed.
