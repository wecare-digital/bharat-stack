# Website-only checkout: legacy-settlement gating, one-time payment claim, and in-WhatsApp capture retirement (v1)

This change closes the three payment-integrity gaps the 2026-10-01 audit left open and reconciles the spec to the owner's website-only ruling. On the Razorpay webhook, the legacy invoice fall-through is now gated on the *typed* reconcile outcome (only `UNKNOWN_REFERENCE` may reach the legacy path, every paid-but-blocked outcome goes to quarantine), the legacy verifier now requires a stored provider-order/payment binding plus a conditional one-time `PROVIDERPAYMENT#<id>` claim, and `_mark_invoice_paid_by_reference` settles exactly one row conditionally or none when ambiguous. The in-WhatsApp payment-capture branch is retired to a type-only audit record with no financial side effects, leaving the Razorpay webhook as the single authoritative payment producer. The spec, a BLOCKED-ON-ENVIRONMENT provisioning runbook, and two new regression tests round it out; no AWS work was executed.

Watch for: a one-time-claim/settlement asymmetry on the legacy path — the irreversible `PROVIDERPAYMENT#` claim is written inside the verifier *before* `_mark_invoice_paid_by_reference` runs, so a settlement that then no-ops (row vanished, became ambiguous, or write failed) burns the claim and leaves the invoice permanently unsettleable by that payment (possible). The dead financial helpers left in the inbound handler after the N1 retirement are harmless but now unreachable on the capture path (confirmed).

**Verdict**: APPROVED

## High-level view

The R1/C1 gate is the load-bearing change: fall-through to the legacy verifier is now keyed on `outcome_kind == UNKNOWN_REFERENCE` rather than `not verified_paid`, so a captured-but-refused commerce outcome (amount/currency/customer mismatch, identity unavailable, provider conflict) can no longer be laundered into a same-priced legacy invoice settlement. Every non-success that isn't a clean `UNKNOWN_REFERENCE` is quarantined.

R2 adds two independent defences inside `_verified_legacy_invoice`: a binding check (the provider order id from the authoritative readback must equal the invoice's stored `providerOrderId`/`order_id`, or the verified payment id must equal the invoice's `providerPaymentId`; an unbound invoice is refused outright) and a conditional `PROVIDERPAYMENT#<payment_id>` claim shared with the commerce path, so one provider payment funds at most one thing overall and a replay under a different reference finds the claim held and settles nothing. `_mark_invoice_paid_by_reference` separately enforces single-row discipline: more than one row on the referenceId GSI is ambiguous and settles none, exactly one settles under a `status <> 'paid'` condition.

The N1 retirement removes all financial side effects from the inbound WhatsApp capture branch — no invoice-paid write, no `completed` order status, no generated receipt, no balance-due notify — replacing them with a type-only superseded audit record. `PAYMENT_LOOKUP_REQUIRED` is deliberately left defined but dead on the money path. The failed/pending/delivery branches, which are non-financial notifications, are untouched.

The spec reconciliation rewrites statements 8 and 10 and the Goals to website-only Razorpay checkout plus a private downloadable receipt, while preserving statement 9's provider-driven-readiness rule verbatim, the paid-only order rule, the reference_id rules, and the admin-Cognito/no-live-send/no-provider-mutation non-goals. The provisioning runbook delivers the missing production pieces as source + IaC + steps, keeps the initiation gate disabled, references secrets only by `{{resolve}}`/ARN, and never claims execution.

### R1/C1: outcome-typed fall-through replaces "any non-success"

The old guard ran the legacy verifier whenever `not verified_paid`, which meant every `PAID_BUT_BLOCKED` outcome — a capture whose money moved but whose commerce attempt was refused — could still be matched to a same-priced invoice and settled. The gate now reads the typed outcome from the reconciler and permits the legacy path only when `outcome_kind == order_creation.UNKNOWN_REFERENCE`:

```python
legacy_invoice_verified = False
if reference_id and not verified_paid and outcome_kind == order_creation.UNKNOWN_REFERENCE:
    legacy_invoice_verified = _verified_legacy_invoice(reference_id, payment, request_id)
```

`UNKNOWN_REFERENCE` is the one outcome that positively indicates no PaymentAttempt exists at all, which is the only state consistent with a genuine pre-commerce invoice-only payment. Every other outcome — the five paid-but-blocked kinds, not-paid, provider-unavailable, error, needs-reconciliation — now goes straight to `_quarantine_unverified_capture`. The test `test_every_paid_but_blocked_outcome_routes_to_quarantine_not_legacy` enumerates the whole `PAID_BUT_BLOCKED_OUTCOMES` frozenset and asserts none settle, so the gate is pinned against the authoritative constant rather than a hand-copied list — if a new blocked outcome is added to `order_creation`, the test covers it automatically.

### R2 binding: amount equality is no longer sufficient

The legacy verifier now reads the capture's provider order id from the authoritative readback (`payment_capture_details`, the new four-tuple variant of `payment_is_captured`) and requires it to match a provider identifier stored on the invoice row:

```python
bound = False
if invoice_order_id and provider_order_id and provider_order_id == invoice_order_id:
    bound = True
if invoice_payment_id and payment_id == invoice_payment_id:
    bound = True
if not bound:
    ... return False
```

An invoice carrying no provider binding at all is refused before this, because amount equality cannot establish that *this* capture settles *this* invoice. The provider order id comes only from the API readback, never the event body — consistent with the codebase's "webhook body is never money authority" discipline. The ambiguity guard tightened the row lookup from `Limit=1` to `Limit=2` specifically so a duplicated referenceId is detected and refused rather than silently picking `items[0]`.

### R2 one-time claim and the claim/settlement asymmetry

`claim_legacy_invoice_payment` writes a conditional `PROVIDERPAYMENT#<payment_id>` marker in the shared commerce-keys namespace before any invoice write. Because it shares the namespace with `claim_order_for_payment`, one provider payment can fund at most one thing across both the commerce and legacy paths, and a replay carrying the same `payment_id` under a different referenceId loses the claim and settles nothing. `test_replay_same_payment_different_reference_does_not_double_settle` drives this end to end against two same-priced, separately-bound invoices and asserts only the first settles.

The asymmetry worth flagging (possible): the claim is irreversible and is taken *inside* `_verified_legacy_invoice`, which returns True before control returns to `_handle_payment_captured` and calls `_mark_invoice_paid_by_reference`. The settle then re-queries the referenceId GSI independently. If that second query sees a state the verifier didn't — a second row appeared (now ambiguous → settles none and quarantines), the row was deleted, or the conditional update raises a non-conditional error — the claim is already burned. The payment is then permanently unable to settle any invoice, including on a legitimate redelivery, while the invoice stays unpaid. This never double-settles (the safe direction), but it can strand a real payment in a state only a human can clear by releasing the claim. The verifier's `Limit=2` ambiguity check and the settle's full-pagination ambiguity check normally agree, so the window is narrow, but the two-query design is what opens it.

### Single-row conditional settlement

`_mark_invoice_paid_by_reference` previously looped and marked every GSI match paid, which would settle a reissue/backfill/forged-collision set off a single capture. It now refuses when more than one row matches (quarantines instead), and settles the single match under `ConditionExpression='#st <> :paid'` so a concurrent or replayed delivery is a harmless no-op logged as `invoice_already_paid_on_settle` rather than an error. A supplied `payment_id` is stamped onto the settled row as `providerPaymentId`. The error-logging change to `type(e).__name__` avoids leaking exception detail into logs. `test_mark_invoice_paid_by_reference_settles_exactly_one_or_none` exercises both the single-row settle and the ambiguous-none branch directly.

### N1: in-WhatsApp capture retired to audit-only

The inbound handler's `_process_payment_status` CAPTURED branch previously accepted a capture fail-open (`PAYMENT_LOOKUP_REQUIRED` defaults off, so an unverified Meta webhook body could mint paid state) and then marked the invoice paid, sent a `completed` order status, generated a GST invoice, and notified balance-due. All four financial effects are gone; the branch now emits a single type-only `in_whatsapp_payment_capture_superseded` record and returns. `verification_outcome` and `lookup_required` are retained in the log for audit continuity, and `PAYMENT_LOOKUP_REQUIRED` is intentionally left defined but dead on the money path — regardless of its value, no paid state is created, which the test `test_capture_remains_retired_even_when_lookup_required_is_on` pins.

The non-financial paths are intact: the `failed` branch still sends the `canceled` notification (asserted non-financial by `test_a_failed_payment_still_notifies_without_settling`), the pending branch still logs and waits, and `_process_status` delivery receipts are untouched. The raw payment record still written before the branch via `_store_payment_record` is a Messages-table audit row, not an invoice settlement. The superseded audit record is deliberately type/correlation-id only — the test asserts the recipient id, transaction id, and amount are absent from the rendered log.

The three financial helpers (`_mark_invoice_paid_by_reference`, `_generate_invoice_for_captured_payment`, `_check_and_notify_balance_due`) remain defined in the inbound handler but have no caller on the capture path now (confirmed by grep). Dead but harmless; a future edit could re-wire them, so retiring or annotating them would make the single-producer invariant harder to regress.

### Provisioning runbook stays BLOCKED and never forces the gate on

The runbook is marked `STATUS: BLOCKED-ON-ENVIRONMENT. Not executed.` and reports each piece (wecare-checkout function, `/ecommerce/*` routes, IAM, S3 bag-icon, alias checkpoint, cancel-only live test) as blocked. It never sets `CHECKOUT_INITIATION_ENABLED` and leaves `EXPECTED_PROVIDER_MID` empty so `payment_readiness` returns `CONFIGURATION_UNVERIFIED` and `prepare_checkout` returns `PAYMENT_INITIATION_DISABLED` — the gate stays disabled by construction, honoring statement 9. Secrets are referenced only by `{{resolve:secretsmanager:...}}` and ARN-scoped IAM; no `get-secret-value`. The cancel-only live monetary test to `+918100640044` is gated on recorded owner authorization, scoped to the minimum provider-accepted amount, self-reversing (immediate cancel/refund), and explicitly never agent-executed.

### Test quality

Both new suites drive the real handler functions against an in-memory DynamoDB fake and stub only the provider readback and heavy downstream (post-payment, lambda invoke, CTWA), then read invoice-row status back from the fake to assert settlement actually did or didn't happen — not static mocks that bypass the control flow. The legacy suite covers blocked-outcome quarantine, two-invoice ambiguity, same-payment replay, the bound positive path, the unbound refusal, and the wrong-provider-order refusal. The inbound suite asserts the forged capture settles nothing, that the financial helpers are not called (fails on revert), that the superseded record is emitted and PII-free, and that failed/delivery paths still work. The orchestrator confirmed both suites fail when the fixes are reverted.

Not tested: the claim/settlement asymmetry window described above (a claim burned by a settle that then no-ops) — no test drives a state change between the verifier's claim and the settle's re-query, so the stranded-payment behavior is unverified in either direction.
