# URL, workspace-link and home-fallback cleanup

Two obsolete public destinations into the staff workspace are gone, one host-canonicalisation
rule was restored to production, and the whole URL/host surface is now pinned by a live probe
harness, a pytest guard on the Amplify rule array and four vitest suites. The planned work —
converting 15 legacy top-level prefixes from `301 → /workspace/<prefix>` into `302 → /` — was
superseded mid-run by the owner's "delete all url redirects now", which closed the same defect
by deletion; the task correctly declined to recreate 45 redirects and documented why. Nothing
was hidden as a substitute for access control: `/workspace/` still answers 200 on the
Authenticator shell and is still `Disallow`ed, and no authorization was removed.

Watch for: the shipped probe harness **exits 1 today** (confirmed) because its
`shop.wecare.digital` expectation was overtaken by a concurrent session closing the subdomain
gap; the matrix document's subdomain section consequently **overstates the gap** (confirmed —
`*.wecare.digital` A+AAAA now exist and arbitrary subdomains 302 to the canonical home); and
the return-path validator still has **no production caller** (confirmed — `sign-in.tsx` keeps
the regex that accepts `//evil` and `/workspace/access`), which is a consequence of the
owner's own do-not-touch constraint rather than an oversight.

**Verdict**: NEEDS_CHANGES

## High-level view

The public-surface half is clean and measured. `ErrorBoundary`'s escape button and the three
PWA `shortcuts` were the only two genuinely public paths into the staff tree; both are gone,
the removal is guarded by a source-text test that also proves the three exemptions
(`Layout`, `SearchModal`, `Breadcrumbs`) really have no importer outside
`src/pages/workspace/**`, and `public/sw.js` is recorded as unverified rather than changed.

The hosting half made exactly one production write: the `https://www.wecare.digital` →
`https://wecare.digital` 301, restored verbatim from the 146-rule snapshot after the owner's
redirect removal deleted it as collateral. I re-measured it: `www /shop/` 301s to apex
`/shop/` with the path preserved, one hop, terminal 200. It is a 301 rather than the brief's
"reversible 302" — correct here, because it is a host canonicalisation, the pre-existing
`retired_url_probe.py` asserts exactly that status, and a 302 on a canonical host rule is the
wrong signal. Worth knowing that 301s are client-cached, so the reversibility is weaker than
the 302 rows.

Everything the brief listed as must-not-break still answers its measured value, which I
verified independently of the task's own harness: `POST /api/razorpay-webhook` 401 with
`content-type: application/json` and `{"error": "Invalid signature"}` — a rejection, not a
page; `/api/auth/validate` 401; `/api/payments/webhook` 404; `/api/webhook/sinch-rcs` 200;
`GET /mcp` 405 and `POST /mcp` 400; `/get/o/...png` 200; `/shop/ /cart/ /orders/ /blog/
/checkout/status/ /checkout/success/` 200; `sitemap.xml`, `llms.txt`, `robots.txt`,
`manifest.json`, `sw.js` and an SVG all 200 with their own content types. The catch-all is
still `/<*>` → `/404.html` at `404-200`, last in the array, and `/definitely-not-a-page/`
returns a real 404 carrying `"page":"/404"`, `noindex, follow` and a canonical to the apex — no
indexable home clone, and no global rewrite serving home HTML for an asset or an API call.

The return-path validator is a correct reject-by-default allowlist. I traced every rejection
class the brief names and each one lands before any allowlist comparison, including the
dot-free `//evil` case the old regex accepted. It returns the value to use rather than a
boolean, and re-emits from the allowlist rather than slicing the input, so an accepted value
cannot carry a query or fragment. It has no caller, so the live open-redirect-shaped gap in
`sign-in.tsx` is still open; the one-line wiring is handed to the `account/**` owner with two
behaviour changes and a third precondition (two allowlisted destinations have no exported
page) stated up front.

Two pieces of evidence have gone stale since they were written, and both are cheap to repair.
The subdomain section documents the coverage gap as not closed and frames it as an
owner-decision item; a concurrent session has since closed it for single-label hosts, so the
document now overstates what is open and the harness's hard assertion on
`shop.wecare.digital` fails. The residual gap is real and exactly as the document predicted —
`a.b.wecare.digital` still has no address, because `*.wecare.digital` matches one label only.

One cross-session hazard sits in the pytest guard: at the reviewed branch tip the two

`provision_legacy_redirects.py` is sitting uncommitted in the shared tree. The committed file

`origin/stack` but not in this branch tip.

## The two public workspace destinations, and what was deliberately left

`ErrorBoundary.handleGoHome` went from the staff dashboard route to a literal `/`, and the
button label from "Dashboard" to "Home". The reasoning is on the record in the file: the
component is mounted inside `_app.tsx`'s `if ( isPublic )` branch, so a customer hitting a
render error on the cart or a blog post was offered a button into a Cognito login they cannot
complete. The old path is deliberately absent from the comment too, because
`PublicWorkspaceLinks.test.ts` asserts the file contains no `/workspace` substring at all — a
comment is exactly what a later edit copies back into a target.

`public/manifest.json` lost the whole `shortcuts` key rather than keeping an empty array. I
confirmed the built export carries no `shortcuts` either.

What was left alone is as important as what moved, and each exemption is a named entry in
`INTENTIONALLY_WORKSPACE_ONLY` rather than a silent gap. The test also asserts the assumption
those exemptions rest on — that no page outside `src/pages/workspace/**` imports `Layout`,
`MaybeLayout`, `SearchModal` or `ui/Breadcrumbs` — which is the part that would otherwise rot.
`public/sw.js:180`'s push-click default is still the staff dashboard and is recorded as
needs-verification; changing it could break staff push with no customer benefit, and nobody
has shown a customer can receive that push.

Nothing here touches authorization. `/workspace/` answers 200 with the Authenticator shell
(`data-amplify-router`, `data-amplify-authenticator-select-mfa-type` present in the body),
`robots.txt` still carries `Disallow: /workspace/` and `Disallow: /api/`, and `robots.txt`'s
own comment already states the model: authentication gates the data, not the HTML.

## The validator

```ts
if ( raw.charCodeAt( 0 ) !== 0x2f ) return DEFAULT_RETURN;
if ( raw.length > 1 && ( raw[ 1 ] === '/' || raw[ 1 ] === '\\' ) ) return DEFAULT_RETURN;
if ( FORBIDDEN_CHARS.test( raw ) ) return DEFAULT_RETURN;
```

`FORBIDDEN_CHARS` is `/[\\\s\u0000-\u001f\u007f%?#:]/`. Traced against the brief's list:
absolute URLs fail the first check (`h` is not `/`); `//evil`, `///evil` and `/\evil` fail the
second; `%2f%2f…` and `%252f%252f…` fail on `%` without ever being decoded; backslashes,
whitespace and control characters fail the class; `..` segments are rejected before the
first-segment check, which matters for `/cart/../workspace/access` whose first segment reads as
`cart`; `javascript:` and `data:` fail the first check and the `:` class. `/workspace/access`
and its siblings fail the blocked-first-segment set, lowercased. The return value is the
normalised allowlist member, so `/cart?x=1` cannot survive as `/cart/` plus a query.

The gap is that nothing calls it. §7 carries the one-line wiring verbatim, names
`src/pages/account/**` as the owner, and lists the two behaviour changes that owner must accept
plus OWNER-DECISION ITEM 4: `/checkout/` and `/account/` are on the allowlist and both measure
404, because `src/pages/checkout/` holds only `status.tsx` and `success.tsx` and
`src/pages/account/` only `sign-in.tsx`. That is pinned by a test that fails the moment a
production caller appears, which is the right trigger point.

## The one production write, and the drift around it

Live rules read back as 12: the host 301, three `/access` → `https://wecare.digital/` 302s
(another session's, applied via the converged provisioner), seven passthrough rewrites and the
`404-200` catch-all. Measured chains:

```
/access/                    302 -> https://wecare.digital/            terminal 200, 1 hop
/access/anything/deep       302 -> https://wecare.digital/            terminal 200, 1 hop
/admin/ /contacts/ /settings/   404 at the requested URL              0 hops
www /shop/                  301 -> https://wecare.digital/shop/       terminal 200, path kept
/definitely-not-a-page/     404  "page":"/404" + noindex + canonical  0 hops
/404/                       200
```

No loops anywhere. The 15 superseded prefixes terminate at 404 and reach home through
`404.tsx`'s `router.replace( '/' )` — a literal, so no path, query or fragment is forwarded,
pinned by `NotFoundFallback.test.ts`. That is the only reading under which the brief's
"land on the canonical home" and "the fallback is still a 404" are both satisfiable, and the
`404.tsx` comment correction says so with the measurement behind it.

The subdomain picture moved after the document was written, and `_row`'s own docstring argues
correctly that `shop.wecare.digital` must stay a hard assertion because it is a surface we
control. It is still the right call — but the expectation is now wrong, so the gate is red:

```
probed 86 row(s); 1 failed; 1 informational row(s) drifted
FAIL GET https://shop.wecare.digital/   [302 -> 200] expect 0
```

Measured directly: `*.wecare.digital` A and AAAA record sets exist in the zone,
`shop.wecare.digital` resolves and 302s to the apex, `zzz-not-a-host.wecare.digital` does the
same, and `a.b.wecare.digital` still fails to connect. So the one-label-only limit the document
predicted is exactly what remains, and the document's own "re-measure, do not re-use" rule is
the instruction it now needs applied to itself.
