What this band is for

The hero claims everyday AI, built for four domains. This band is where that claim gets its evidence: the terminal shows many services on one foundation, and the copy column says what that buys a customer. So the panel existing is a decision, not a defect. What follows is only about whether it does that job in the states a visitor actually meets.

IMPROVED

F1 — The panel no longer empties itself, but it still starts mostly empty

.wt-space

The terminal is 650px tall — the biggest single thing on a 2090px page. Two of the three causes are fixed. The 600ms delay before the first step is gone, so arrival now shows one step rather than nothing: 75% empty instead of 95%. And the sequence no longer resets — it used to drop back to a single line every 15.8s, so the empty state recurred for as long as you stayed on the page. It now happens once.

What is still true: the first thing a visitor sees is a 650px panel with one line in it, filling over ~12.5s. Making it start fuller means seeding several steps, which weakens the "watch it happen" idea — still a decision, still listed at the end.

STILL OPEN

F2 — By the end, 4 of the 8 steps have scrolled out and cannot be recovered

.wt-space · overflow-y:auto · aria-hidden

At completion 1350px of content sits in a 551px box — 245% — and the component auto-scrolls to follow the newest step (parentElement.scrollTop = scrollHeight). The frame above, scrolled to 799px exactly as the live page is, is the proof: 4 steps are entirely above the visible edge and 1 more is cut in half. On the phone frame it is 6 of 8.

Counted, not inferred from the overflow arithmetic: a step is only hidden when its whole box is past the edge, which is a different question from how much total height overflowed.

Nobody can scroll back to them. The scroll container is aria-hidden="true" with no tabindex, so it is not reachable by keyboard (WCAG 2.1.1) and not exposed to assistive tech at all. A mouse user can wheel over it — and then the next step auto-scrolls them away again. So the panel streams four steps that no visitor can read, and the parallel-lanes step is the one carrying the band's strongest claim.

why the frame can show this at all

A cloned DOM node loses its scroll position, and scroll position is this finding — a snapshot taken without it would show the stream from the top, i.e. show content the visitor cannot see and hide the defect. So the live scrollTop is carried across as data-scrolltop and restored by the one three-line script in each frame.

FIXED

F3 — .wt-infra failed AA, and it is the line carrying the band's claim

was rgba(255,255,255,.44) → 4.25:1 · now .50 → 5.28:1

Every colour in this panel is a white alpha over #000, and an alpha is not a colour until it is composited — so these ratios are computed from the painted pixel, not looked up. Thirteen of the fourteen text styles passed. The one that did not was the # comment line naming the shared infrastructure in each step — which is precisely the line that makes the band's argument.

Fixed: .44 → .50, and nothing else. Deliberately not .62: that is .wt-desc's value, and the infra line is meant to read as substrate beneath the description rather than level with it. .50 is the smallest step that clears AA and keeps that order. All fourteen now pass — the left frame below restores the old value so the comparison still means something; the right frame is what ships.

LOW

F4 — The sticky copy column has 136px of travel

.home-flow-copy{position:sticky;top:128px}

The copy column is 514px inside a 650px band, so sticky can hold it for 136px of scroll and no more before the band's bottom edge pushes it out. Below 1024px the rule is switched off entirely (position:static;order:-1). The two frames are near-identical, which is the point — this is ~136px of behaviour and a top:128px magic number that has to track the header height.

MED

F5 — With no JavaScript the band is a black rectangle

the crawler and failed-bundle state

The stream is rendered by React state, so without it the panel is chrome and one line. The copy column is unaffected — it is static markup — so the band still says its thing; what is lost is all of the evidence for it. Worth knowing because band 3 deliberately solved this exact problem the other way round, with the .is-armed pattern: it ships the final state and lets JavaScript hide it.

DECISIONS

Not mine to take

F3 is the only finding here with a fix that carries no design content, which is why it is the only one with an “after” frame. The rest change what the band says:

#The questionWhy it is a decision
F1Should the panel ship already populated? Partly done. The 600ms dead start and the 15.8s reset are gone, so arrival is one step rather than none and the empty state no longer recurs. Seeding several steps is what remains, and that weakens the “watch it happen” idea.
F2Eight steps, or fewer that fit? 1350px does not fit 551px. Either the panel grows, the steps get shorter, or four of them are cut. All three change the argument.
F2Should the stream be pausable? Resolved WCAG 2.2.2 applies to content moving automatically for over 5s; this ran 15.8s on a loop with no pause, stop or hide. It now plays once and holds, which is the conformant answer that adds no furniture to the page — and it matches what the closing band already does for the same stated reason. The rotating headline in band 1 still has this exposure at 9.6s, and is now the only one left.
F4Keep sticky for 136px? Dropping it removes a magic number; keeping it is a real if small effect.
F5Should the no-JS state carry the steps? Band 3's .is-armed pattern is the in-repo precedent for doing so.
