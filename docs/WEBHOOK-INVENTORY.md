## Plivo — current state (recorded 2026-09-19)

| Application name | `WECARE-WHATSAPP-IVR` |

| Hangup URL | `POST https://api.wecare.digital/plivo/answer` |
| Fallback Answer URL | `POST https://api.wecare.digital/plivo/answer` |
| SIP trunk alias | `WECARE-WhatsApp-IVR-SIP` |
| SIP URI / username | not recorded here — keep with the trunk credentials in Secrets Manager |

Answer URL == Hangup URL is **intended**: Plivo hits the same endpoint twice per
call and the handler sends the follow-up SMS only when `CallStatus=completed`,
so one call yields exactly one SMS (`handler.py:205-210`).

### ⚠️ The endpoint is unauthenticated, and it can send SMS

Measured 2026-09-19 against the live account:

- `POST /plivo/answer` on API `zllr9lrg7j` — `AuthorizationType: NONE`,
  no authorizer, `ApiKeyRequired: false`.
- `wecare-plivo-answer` env vars are `DLT_TEMPLATE_KEY`, `IVR_AUDIO_URL`,
  `POST_CALL_SMS_ENABLED`, `SMS_FUNCTION`. **`PLIVO_ANSWER_TOKEN` is not set**,
  so `ANSWER_TOKEN` is `''` and the `if ANSWER_TOKEN and ...` gate at
  `handler.py:167` never runs.
- None of the three Plivo URLs above carry a `?token=` query string.
- No reserved concurrency on the function; the `prod` stage allows 100 rps /
  200 burst.

Consequence: an unauthenticated caller can POST
`CallStatus=completed&From=91XXXXXXXXXX` and cause a DLT-templated SMS to be
sent to any Indian mobile via `wecare-sms-aws:live`, at up to the stage throttle.
That is both a cost/abuse vector and TRAI/DLT exposure, since the messages go out
under the registered entity and template `ivr-default`.

Closing it requires a change on both sides, in this order, for zero downtime:

1. Add `?token=<value>` to all three Plivo URLs. Harmless while the Lambda has
   no token, because the gate stays off.
2. Then set the token on `wecare-plivo-answer`. The gate activates and matches.

Doing it in the reverse order 403s every inbound WhatsApp call in between, and
the caller hears silence.

Also worth noting: **the Fallback Answer URL is the same as the Answer URL**, so
it provides no fallback. If the primary fails, Plivo retries the identical
Lambda behind the identical route and gets the identical failure.

## Razorpay setup, manual

1. Dashboard → **Settings → Webhooks → Add New Webhook**
2. Webhook URL: `https://api.wecare.digital/razorpay-webhook`
3. Secret: must match the `webhook_secret` field in Secrets Manager secret
   `wecare/razorpay-webhook`. If you change one, change both, or signature
   verification fails and every payment webhook is rejected.
4. Select the events listed above.
5. Save, then use **Send Test Webhook** and confirm a 200.
